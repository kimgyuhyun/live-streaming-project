2차 검토 보완 5건

기능 범위는 그대로이고, 구현할 때 빠지기 쉬운 부분을 채웠다. 본문의 해당 위치에는 추가 표시를 달았다.

항목문제반영반영 위치
화질 자동 전환MediaMTX는 경로 하나가 화질 하나다. 원본 경로와 FFmpeg가 만든 720p 경로가 따로 생기고, 둘을 묶은 master playlist는 만들어 주지 않는다. 이게 없으면 hls.js가 화질을 자동으로 바꾸지 못한다두 경로의 playlist를 묶는 master playlist를 직접 만든다(nginx 또는 Spring). 1주차 송출 → 재생 확인 때 같이 확인한다기본 골격 · 1주차에 확인할 것
비로그인 시청자 수 집계HLS 시청은 파일을 요청하는 것뿐이라, 서버가 지금 보고 있는 사람을 알기 어렵다시청 페이지는 로그인 여부와 상관없이 채팅 WebSocket에 붙는다(비로그인은 읽기 전용). 시청자 수 = 방송별 WebSocket 연결 수로 센다기본 골격 · 세부 설계 때 정할 것
스트림 키 재발급 시 송출 차단MediaMTX는 송출을 시작할 때만 키를 확인한다. 키를 재발급해도 이전 키로 이미 송출 중인 방송은 계속된다재발급할 때 송출 중인 방송이 있으면 MediaMTX API로 그 연결을 끊는다기본 골격
LL-HLS 프록시 설정LL-HLS는 서버가 응답을 잡아두는 방식의 playlist 요청을 쓴다. Caddy → nginx를 거치면서 버퍼링되거나 타임아웃이 짧으면 지연이 늘어난다nginx /hls에 proxy_buffering off와 넉넉한 읽기 타임아웃을 준다. 배포 주소에서 실제 지연(2~4초 목표)을 잰다기술 스택(앞단) · 1주차에 확인할 것
“서버 2대” 표현실제로는 같은 오라클 서버의 Spring 컨테이너 2개다. “서버 2대”라고만 쓰면 면접에서 물리 서버 2대로 오해받을 수 있다README와 구조도에 “같은 머신에서 인스턴스 2개를 띄워 Redis Pub/Sub 전달을 검증했다”라고 적는다기술 스택(백엔드) · 마무리 산출물

2주실시간 채팅(서버 2대 전달, 비로그인 읽기 전용, 도배 제한), 동시 시청자 수, 즐겨찾기, 자동 썸네일동시 접속 N명에서 채팅 전달 지연 p95를 기록한다
3주가상 재화 후원, 탐색·검색, README와 GIF 3개, 데모 방송 상시 켜기동시 후원으로 잔액 오류를 먼저 재현하고, 방어 전후 실패 건수를 기록한다. 배포 주소에서 방송 → 채팅 → 후원 흐름이 이어진다. README에 수치 3개와 GIF 3개가 들어간다

데모 방송

방송하는 사람이 본인 하나뿐이라, 프로그램으로 방송하는 사람을 흉내 내서 여러 방송이 동시에 도는 상태를 만든다.

구조

구분방송하는 쪽서버가 하는 일
실제 방송 (본인)OBS Studio스트림 키 검증 → 1080p 원본 + 720p 변환
데모 방송 3~5개서버 안에서 도는 FFmpeg가 영상 파일을 반복 송출. 테스트 스트리머 계정마다 스트림 키 하나씩스트림 키 검증 → 원본 하나만 전달, 변환 없음
  • 데모 방송도 실제 방송과 같은 경로(스트림 키 검증 → 수신 → HLS 전달)를 탄다. 방송 목록, 시청자 수, 썸네일, 채팅이 모두 실제로 동작한다.
  • 데모 방송은 변환 없이 원본만 보낸다. 방송 1개당 CPU는 몇 % 수준으로 예상하고, 1주차에 측정한다. 2코어는 본인 방송의 720p 변환에 쓴다.

기술 스택

서버가 2코어라서 CPU를 아끼는 쪽으로 골랐다. 마지막 칸은 각 구성 요소가 서버 CPU를 얼마나 쓰는지.

영역선택이유서버 CPU
프론트React + Vite + TypeScript, React Router, React Query, hls.js방송 목록·채팅은 몇 초마다 바뀌어 SSR 이점이 적다. 치지직과 같은 구조(React + Vite SPA + hls.js). Next.js는 이미 써 봤다0 (정적 파일, Node 서버 없음)
