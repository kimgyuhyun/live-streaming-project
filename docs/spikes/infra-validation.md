# 인프라 검증 (로컬)

이슈를 쓰기 전에, 직접 띄워 봐야만 알 수 있는 것을 확인한 기록이다.
검증용 임시 코드(인증 서버, 설정 변경)는 `spike/infra-validation` 브랜치에만 있고 main에 합치지 않는다.

- 환경: Windows + Docker Desktop, MediaMTX 1.21.4, ffmpeg 8.1.2, OBS Studio 33.0.0
- 서버(2코어 ARM)에서 재야 하는 값(CPU 등)은 여기서 판단하지 않는다.

## 1. 스트림 키 검증과 송출 끊기 — 2026-11-20

### 방법

- MediaMTX `authMethod: http`로 키 확인 요청을 임시 인증 서버(Node)로 보냈다. 임시 서버는 요청을 기록하고, `publish`는 `key`가 맞을 때만 200, 아니면 401을 돌려준다.
- ffmpeg 테스트 영상과 OBS로 송출했다.
- 송출 끊기는 MediaMTX API(`api: yes`, 내부 포트 9997)로 했다.

### 결과

| # | 테스트 | 결과 |
| --- | --- | --- |
| A | 틀린 키로 송출 | 401 → 거부, ffmpeg 종료 |
| B | 키 없이 송출 | 401 → 거부 |
| C | 맞는 키로 송출 | 200 → 송출 시작. path는 `live/ch1`, 키는 `query`로 분리되어 온다 |
| D | HLS 시청 (기본 설정) | 시청도 인증 요청이 간다(`action: read`). HTTP 요청 22번에 인증 2번 — 요청마다가 아니라 시청 세션마다 확인한다 |
| E·F | API로 송출 연결 찾기 → 끊기 | `GET /v3/rtmpconns/list` → `POST /v3/rtmpconns/kick/{id}` 200. 송출 종료, 시청 주소 404 |
| G | `authHTTPExclude`에 `read`·`api` 추가 | 인증 서버로는 `publish`만 간다 |
| H | 인증 서버가 꺼진 상태에서 맞는 키로 송출 | 거부(연결 실패도 거부로 처리) |
| I | OBS 송출 중, 키가 유효한 상태에서 끊기 | OBS가 약 2초 뒤 자동 재접속해서 다시 송출된다 |
| J | 키를 바꾼(재발급) 뒤 끊기 | OBS가 약 7초 간격으로 재접속을 시도하지만 매번 401 → 송출 중단 |
| - | 송출 중 인증 서버 재시작 | 이미 송출 중인 방송은 영향 없음 (송출 시작 때만 확인한다) |

MediaMTX가 인증 서버로 보내는 요청 (POST, JSON):

```json
{
  "ip": "172.27.0.1", "user": "", "password": "", "token": "",
  "action": "publish", "path": "live/ch1", "protocol": "rtmp",
  "id": "d6e341cb-…", "query": "key=secret123",
  "userAgent": "FMLE/3.0 (compatible; FMSc/1.0)"
}
```

### 설계에 반영할 것

1. **송출 주소:** `rtmp://{서버}/live/{채널ID}?key={스트림키}`. OBS에서는 서버 `rtmp://{서버}/live`, 스트림 키 `{채널ID}?key={스트림키}`로 입력한다(OBS로 확인). 키가 path에 들어가지 않아서 시청 주소에 노출되지 않는다.
2. **인증 엔드포인트(Spring):** `action == publish`일 때 `path`의 채널ID와 `query`의 키를 대조한다. 2xx면 허용, 그 외는 거부. Spring이 죽으면 새 송출은 막힌다(진행 중인 방송은 유지).
3. **인증에서 제외:** `authHTTPExclude`에 `read`, `api`. 시청은 공개이고, API는 기본으로 인증을 거치기 때문에 빼지 않으면 Spring이 API 호출까지 판단해야 한다.
4. **API는 내부망에만:** 연결 목록 응답의 `query`에 스트림 키가 그대로 보인다. 호스트 포트로 열지 않는다.
5. **키 재발급 순서:** DB에서 이전 키를 먼저 무효화하고, 그다음 송출 연결을 끊는다. 끊기만 하면 OBS가 2초 만에 이전 키로 다시 붙는다(I).
6. **끊을 연결 찾기:** `rtmpconns/list`에서 `state == publish`이고 `path == live/{채널ID}`인 항목의 `id`.
7. **MoQ 끄기:** 1.21부터 MoQ 서버가 기본으로 켜져 있다. `moq: no`.

### 참고

- 인증 요청의 `ip`는 도커 게이트웨이 주소(172.27.0.1)였다. 송출자 실제 IP가 필요한 기능은 없어서 문제 삼지 않는다.
- 키가 틀려 거부당한 OBS는 최대 재시도 횟수까지 계속 재접속을 시도하고, 그때마다 인증 요청이 온다.

## 2. 720p 변환과 master playlist — 2026-11-20

### 방법

- MediaMTX 이미지를 `1.21.4-ffmpeg`로 바꾸고, `live/{채널}`이 준비되면(`runOnAvailable`) ffmpeg가 720p로 변환해 `720/{채널}`로 다시 송출하게 했다.
- ffmpeg 테스트 영상 1080p 30fps, 6Mbps, 키프레임 2초(`-g 60`)로 송출했다.
- 720p 설정: `libx264 veryfast zerolatency`, 2.5Mbps, `-force_key_frames source`(원본 키프레임 위치에 맞춤), 오디오는 복사.

### 결과

| # | 확인 | 결과 |
| --- | --- | --- |
| K | 변환 경로 | `live/ch1` 준비 → 약 4초 뒤 `720/ch1` 준비. 1280x720, H264 + AAC |
| L | 내부 ffmpeg의 재송출 인증 | `720/ch1` publish 요청이 `ip: ::1`, `query: ""`로 인증 서버에 온다 |
| M | 실시간 처리 | 30.7초 동안 원본·720p 모두 세그먼트 15개(2초짜리) 생성 → 실시간을 따라간다 |
| N | CPU (참고용, x86 로컬) | MediaMTX 컨테이너 41~52%. 컨테이너 상한 `cpus: 0.5`에 거의 붙어 있다 |
| O | 세그먼트 길이 | 원본 키프레임 간격과 같다(2초). 키프레임 간격이 길면 세그먼트도 길어진다 |
| P | 두 화질의 시각 기준 | 같은 화면인데 720p의 PROGRAM-DATE-TIME이 원본보다 약 0.4초 늦다. MediaMTX가 받은 시각으로 매기기 때문에 변환 지연만큼 밀린다. 원본 복사본과 720p를 ffmpeg 하나로 같이 내보내 봤지만 차이가 0.87초로 오히려 커져서 되돌렸다 |
| Q | MediaMTX의 master playlist를 거치지 않고 화질별 playlist 직접 요청 | 401 `session not found`. MediaMTX는 `index.m3u8` 요청마다 시청 세션을 만들고, 화질별 playlist 주소에 `?session=…`을 붙여 준다 |
| R | 세션을 다른 IP에서 사용 | 401. 세션은 만든 IP에 묶여 있다 |
| S | 세션 30초 미사용 후 | 그대로 200 (30초 안에는 만료되지 않음) |
| T | 시청 세션 목록 API | `GET /v3/hlssessions/list`에 path·remoteAddr·userAgent와 함께 나온다 |

### 설계에 반영할 것

1. **master playlist는 서버(Spring)가 미리 만들 수 없다.** 세션이 IP에 묶여 있어서, Spring이 MediaMTX에서 받아 온 세션 주소를 브라우저가 쓰면 401이 난다. 두 화질의 `index.m3u8`을 **브라우저가 직접**(nginx 경유) 받아서, 세션이 붙은 화질별 주소로 master playlist를 조립해 hls.js에 넘겨야 한다. → 3번에서 hls.js로 확인한다.
2. **화질 전환 때 끊김 위험:** 두 화질의 시각 기준이 약 0.4초 어긋나 있다. hls.js가 화질을 바꿀 때 이 차이를 견디는지 3번에서 확인한다. 못 견디면 대안은 (a) 화질 자동 전환 대신 수동 선택(바꿀 때 다시 불러오기), (b) 720p 빼기.
3. **내부 재송출 인증:** `720/*` publish는 `ip`가 `127.0.0.1` 또는 `::1`일 때만 허용한다. 외부에서 `720/*`로 송출하는 것을 막아야 한다(RTMP 포트는 공개).
4. **CPU 상한:** 변환을 켜면 MediaMTX 컨테이너 `cpus: 0.5`로는 빠듯하다(x86 로컬 기준). 서버(ARM)에서 실측해서 정한다.
5. **OBS 키프레임 간격:** OBS 기본값(0 = 자동)은 키프레임 간격이 길어 세그먼트가 길어진다. 송출 안내에 키프레임 간격 1~2초 설정을 넣는다.
6. **설정 이름:** 1.21에서는 `runOnReady`가 아니라 `runOnAvailable`이다(이전 이름도 동작은 한다).

### 참고 — 시청자 수

`/v3/hlssessions/list`로 경로별 시청 세션(비로그인 포함)을 셀 수 있다. 기획서 v4는 "채팅 WebSocket 연결 수로 센다"고 정했는데, 이 방법도 후보가 된다. 세션이 몇 초 동안 요청이 없으면 닫히는지는 확인하지 않았다.

## 3. hls.js 재생, 화질 전환, 지연 — 2026-11-20

### 방법

- 임시 페이지(`frontend/public/spike/player.html`, hls.js 1.7.4, `lowLatencyMode: true`)를 Vite 개발 서버로 띄우고, 브라우저 패널에서 열어 hls.js 이벤트를 로그로 모았다.
- 브라우저가 `live/ch1`과 `720/ch1`의 `index.m3u8`을 받아, 화질별 주소로 master playlist를 조립해 Blob URL로 hls.js에 넘겼다.
- 지연(`pdtLag`) = 현재 시각 − 지금 재생 중인 위치의 PROGRAM-DATE-TIME. MediaMTX가 영상을 받은 시점부터 화면에 나올 때까지다. OBS 인코딩과 RTMP 전송 시간은 포함하지 않는다(눈으로 재는 화면 간 지연은 재지 않았다).
- Vite 프록시를 거쳤다. nginx·Caddy를 거친 지연은 서버에서 잰다.

### 결과

| # | 확인 | 결과 |
| --- | --- | --- |
| U | 조립한 master playlist | hls.js가 받아들인다. 화질 2개(720p, 1080p) 인식, 720p로 시작해 약 1초 만에 1080p로 자동 상승 |
| V | 1080p 재생 지연 | `pdtLag` 약 2.1초로 안정, 버퍼 약 1초, 프레임 손실 0 |
| W | 자동 전환으로 720p로 내리기(`autoLevelCapping=0`) | **재생이 멈췄다.** 14초 동안 화면이 정지했고 720p로 넘어가지도 못했다(`bufferStalledError`) |
| X | 상한 해제 → 1080p 복귀 | 13초 분량을 건너뛰고 재생 재개, 지연 3.4초로 증가 |
| Y | 즉시 전환으로 720p(`currentLevel=0`) | 약 3.4초 멈춘 뒤 720p 재생, 지연 3.0초 |
| Z | 다시 자동(1080p) | 약 1초 멈춤, `bufferSeekOverHole`, 지연 5.7초로 늘어난 채 유지 |
| AA | 1080p 단독 재생(조립 없이 `live/ch1/index.m3u8`) | 0.65초 만에 재생 시작, 지연 2.19초 안정 |
| AB | 720p 단독 재생(`720/ch1/index.m3u8`) | 0.75초 만에 재생 시작, 지연 2.94초 안정(변환 지연 포함 실제로는 원본보다 더 늦다) |

참고: 브라우저에서는 쿠키가 동작해서 화질별 주소에 `?session=`이 붙지 않았고, 조립한 master에서도 401이 나지 않았다.

### 결론

1. **화질 자동 전환(ABR)은 지금 구조로는 쓸 수 없다.** 두 화질이 MediaMTX의 서로 다른 경로라 타임라인이 맞지 않는다. 전환할 때마다 수 초씩 멈추고, 지연이 계속 쌓인다(2.1초 → 5.7초).
2. **화질별 단독 재생은 문제없다.** 시작 0.7초 안팎, 지연 2~3초로 LL-HLS 목표(2~4초) 안이다.
3. **대안:**
   - (a) **수동 화질 선택:** 화질을 고르면 그 경로의 `index.m3u8`로 다시 불러온다. 바꿀 때 약 0.7초 끊긴다. master playlist 조립이 필요 없다.
   - (b) **720p 빼기:** 원본 하나만 보낸다. 변환 CPU(약 1코어)도 아낀다.
   - (c) 패키저 바꾸기(ffmpeg가 정렬된 여러 화질 HLS를 직접 만들기): ffmpeg의 HLS 출력은 LL-HLS를 지원하지 않아서 지연이 커진다. 3주 범위에서는 하지 않는다.
4. 기획서의 "웹 플레이어가 화질 자동 전환"과 2차 검토 보완 "master playlist 직접 생성"은 고쳐야 한다. (a)/(b) 중 무엇으로 갈지는 서버 CPU 실측 뒤에 정한다.

## 4. 시청 세션이 닫히는 시간 (2026-11-26, 시청자 활동 PRD)

`docs/result/prd/viewer.md` V1(동시 시청자 수를 세는 방법)을 정하려고 쟀다. 1절 T와 "참고 — 시청자 수"에서 남겨 둔 "세션이 몇 초 동안 요청이 없으면 닫히는지"를 확인했다.

### 방법

- 로컬 도커 전체 실행(MediaMTX 1.21.4, nginx 경유 `:8000`), 데모 방송 `live/62`.
- `curl`(쿠키 저장 켬)로 `/hls/live/62/index.m3u8`을 1초마다 6번 요청한 뒤 멈췄다.
- Spring 컨테이너 안에서 `GET /v3/hlssessions/list`의 `itemCount`를 3초마다 읽었다.

### 결과

| # | 확인 | 결과 |
| --- | --- | --- |
| AC | 요청 6번이 만든 세션 수 | **6개.** 요청마다 새 세션이 생겼다(쿠키 확인 리다이렉트를 거친 `curl`은 세션을 이어 쓰지 못했다). 브라우저는 쿠키로 세션을 이어 쓴다(1절 참고) |
| AD | 마지막 요청 뒤 세션이 닫힐 때까지 | 약 **25~30초.** 멈춘 뒤 21초까지 6개 그대로, 24초부터 줄어 33초에 0 |

### 결론

- MediaMTX 세션 수로 세면 시청자가 나간 뒤 약 30초 동안 숫자가 남는다. 확정 사양 7절 "최대 10초 늦게"를 넘는다. 이 시간을 설정으로 줄일 수 있는지는 확인하지 않았다.
- 쿠키를 쓰지 않는 클라이언트는 요청마다 세션을 만든다. 스크립트로 시청자 수를 쉽게 부풀릴 수 있다.
