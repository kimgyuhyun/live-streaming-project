# PRD — 채널·송출 (channel)

> 상태: **확정** (2026-11-20) — 기술 결정 3건과 하지 않을 것을 사용자가 확정했다. 3안 비교 원본은 `docs/result/adr/channel.md`.
> 규칙(숫자·조건)의 원본은 `docs/result/spec-fixed.md` 3절(스트리머·채널), 4절(스튜디오), 5절(방송 송출과 시청), 10절(데모 방송)이다. 썸네일(5절)은 탐색 도메인에서 다룬다.
> 미디어 서버 동작의 근거는 `docs/spikes/infra-validation.md` 1절이다.

## 개요

회원이 스트리머가 되고(신청 → 운영자 승인), 채널과 스트림 키를 받아 OBS로 송출하면 방송이 시작되고, 누구나 그 방송을 보는 데까지를 다룬다. 데모 방송도 같은 경로로 띄운다.

**승인제를 두는 이유:** 큰 플랫폼은 누구나 송출하게 두고 본인인증·자동 탐지·24시간 대응으로 사후에 막는다. 1인 운영·무료 클라우드에서는 그 체계를 갖출 수 없고, 불법 영상 한 번에 서버 계정이 정지될 수 있어서, 아는 사람만 송출하게 해 사후 대응이 필요한 상황 자체를 막는다. 공개로 바꾸려면 본인인증과 신고·자동 차단부터 갖춰야 한다.

이 도메인은 계정 도메인(`prd/member.md`)의 인증·역할 위에 선다. 방송 상태(방송 중인지, 언제 시작했는지)는 채팅·시청자 수·목록·후원이 모두 읽어 간다.

## 사용자 스토리

| # | 스토리 |
| --- | --- |
| 1 | 회원으로서, 스트리머 신청을 하고 결과(대기·승인·거절)를 보고 싶다. 승인돼야 방송할 수 있기 때문이다 |
| 2 | 운영자로서, 대기 중인 신청을 보고 승인하거나 거절하고 싶다. 모르는 사람이 서버로 아무 영상이나 내보내지 못하게 하려는 것이다 |
| 3 | 스트리머로서, 승인되면 채널이 바로 생기고, 스튜디오에서 키를 발급받아 OBS에 넣기만 하면 방송할 수 있으면 한다 |
| 4 | 스트리머로서, 키가 샜다고 생각되면 재발급하고, 이전 키로 하던 송출은 즉시 끊기고 다시 붙지 못했으면 한다 |
| 5 | 스트리머로서, 방송 제목을 미리 정하거나 방송 중에 바꾸고, 지금 송출이 들어오고 있는지 스튜디오에서 보고 싶다 |
| 6 | 스트리머로서, 채널 이름과 소개를 바꾸고 싶다 |
| 7 | 시청자(비로그인 포함)로서, 채널 페이지에서 방송 중이면 바로 보고, 아니면 오프라인임을 알고 싶다 |
| 8 | 운영자로서, 내가 방송하지 않는 시간에도 사이트에 방송 몇 개가 떠 있었으면 한다(데모 방송). 면접관이 아무 때나 사이트를 열어 본다 |

## 기술 결정

### C1. 스트림 키는 해시와 앞 4자리만 저장한다

**Context** — 확정 사양: 키 전체는 발급·재발급 직후 한 번만 보여 주고 그 뒤로는 앞 4자리만, 재발급하면 이전 키는 즉시 무효. 송출 시작 때 MediaMTX가 넘긴 키를 확인해야 한다. DB가 새도 남이 방송할 수 있으면 안 된다.

**Decision** — 채널에 키의 SHA-256 해시(되돌릴 수 없는 고정 길이 값)와 앞 4자리만 저장한다. 발급·재발급 응답에만 전체 키를 담는다. 확인할 때는 들어온 키를 해시해 일정 시간 비교(`MessageDigest.isEqual` — 어디서 달라지든 같은 시간이 걸리는 비교)로 맞춘다. 키는 32바이트 난수라 BCrypt 같은 느린 해시가 필요 없다.

**Alternatives**
- B. 평문 저장 — DB가 새면 모든 채널로 송출할 수 있다. "한 번만 보여 준다"를 코드로 지켜야 해서 실수로 응답에 넣기 쉽다.
- C. 암호화 저장 — 다시 보여 줄 수 있다는 장점이 확정 사양에서는 필요 없고, 서버 비밀키 관리만 늘어난다.

**Consequences**
- 저장된 값으로 키를 다시 만들 수 없어서 "한 번만 보여 준다"가 구조로 지켜진다. 조회 API가 앞 4자리만 주는지는 테스트로 박는다.
- 키를 잃어버리면 재발급해야 한다(확정 사양과 같다).
- 서버 밖에서 키를 쓰는 쪽(데모 시뮬레이터)은 발급 응답의 키를 직접 보관해야 한다 → C3.
- **다시 여는 조건:** "키 다시 보기" 요구가 생기면 C(암호화)를 검토한다.

### C2. 방송 시작·종료는 MediaMTX 훅으로 받고, 1분마다 대조한다

**Context** — 송출이 들어오면 "방송 중", 끊기면 "방송 종료"가 되어야 하고, 채널 페이지·스튜디오 연결 상태·방송 목록·채팅·후원이 이 상태를 읽는다. 키 확인 요청은 "송출해도 되나"만 묻는 것이라, 통과해도 실제로 영상이 들어온다는 보장은 없다.

**Decision**
- MediaMTX가 `live/{채널ID}` 경로의 방송이 준비되면(`runOnAvailable`) / 끊기면(`runOnUnavailable`) `wget`으로 Spring 내부 주소(`/internal/`)에 알린다. 알림이 실패해도 MediaMTX는 다시 시도하지 않는다.
- Spring은 1분마다 MediaMTX API(`/v3/paths/list`)로 지금 송출 중인 경로를 가져와 DB의 진행 중 방송과 맞춘다(없는데 진행 중이면 종료, 있는데 기록이 없으면 시작).
- 알림과 대조는 **같은 처리 함수**를 쓰고 멱등(같은 알림을 두 번 받아도 결과가 같은 성질)이다. "채널당 진행 중인 방송은 하나"를 DB 제약으로 건다 — 서버 2대가 동시에 대조해도 방송이 두 번 시작되지 않는다.
- 훅 명령에 셸과 `wget`이 필요하므로 MediaMTX 이미지를 `bluenviron/mediamtx:1.21.4-ffmpeg`(Alpine 기반)로 바꾼다.

**Alternatives**
- A. 훅만 — MediaMTX가 재시작되거나 알림 순간 Spring이 둘 다 죽어 있으면 끝난 방송이 계속 "방송 중"으로 남고, 고칠 길이 없다.
- B. 주기적 조회만 — 반영이 조회 간격만큼 늦다. 짧게 잡으면 서버 2대가 몇 초마다 같이 조회한다.

**Consequences**
- 평소에는 거의 즉시 반영되고, 알림을 놓쳐도 최대 1분 뒤에 맞는다.
- 처리 길이 둘이라, "알림 없이 대조만으로 시작·종료가 맞춰진다"와 "같은 알림을 두 번 받아도 방송은 하나"를 테스트로 박는다.
- MediaMTX 이미지가 커진다(ffmpeg 포함). 720p를 켜면 어차피 필요한 이미지다.
- 훅 알림은 인증 없이 내부망에서만 받는다. nginx가 `/internal/`을 넘기지 않는 것을 테스트(nginx 설정 확인)로 박는다.
- **다시 여는 조건:** 방송 상태가 1분 넘게 틀리는 일이 실제로 보이면 대조 간격을 줄이거나 B로 바꾼다.

### C3. 데모 방송은 준비 스크립트가 실제 흐름을 밟아 만든다

**Context** — 확정 사양 10절: 데모 스트리머 3~5개가 서버 안에서 영상 파일을 반복 송출한다. 데모도 실제 방송과 같은 경로(키 확인 → 수신 → 시청)를 타고, 데모 스트리머는 본인이 승인한 테스트 계정이다. C1 때문에 서버에는 키의 해시만 있다.

**Decision** — 준비 스크립트가 공개 API로 가입 → 스트리머 신청 → 운영자 계정으로 승인 → 키 발급(이미 있으면 재발급)을 실제로 하고, 그 응답의 키를 시뮬레이터 설정 파일(git 제외)에 적는다. 시뮬레이터(FFmpeg 컨테이너)는 그 파일의 키로 `live/{채널ID}?key=…`에 송출한다. 데모 채널 표시는 운영자가 채널에 붙인다(운영자 API).

**Alternatives**
- A. 앱 시작 때 환경변수로 데모 스트리머를 바로 만들기 — 신청·승인을 건너뛰어 "본인이 승인한 계정"이 아니다. 데모 키가 `.env`에 평문으로 있다.
- B. 데모 경로는 키 확인을 건너뛰기 — 같은 경로(키 확인)를 타지 않아 확정 사양과 어긋난다. 키 확인에 예외 분기가 생긴다.

**Consequences**
- 서버 코드가 늘지 않는다. 스크립트가 1주차 기능 전체를 처음부터 끝까지 한 번 도는 확인이 된다.
- 데모 이슈는 가입·신청·승인·재발급 이슈가 다 끝난 뒤에 온다.
- 스크립트를 다시 돌리면 키가 재발급되어 돌던 데모 송출이 끊긴다. 시뮬레이터는 새 키로 다시 시작한다.
- 서버(배포)에서는 운영자 비밀번호로 스크립트를 한 번 돌려야 한다.
- **다시 여는 조건:** 데모 계정을 자주 새로 만들어야 하는 상황(DB를 자주 비우는 환경)이 생기면 A를 검토한다.

### 검증에서 이미 정한 것 (비교 없이 옮김)

| 결정 | 내용 | 근거 |
| --- | --- | --- |
| 송출 주소 | `rtmp://{서버}/live/{채널ID}?key={스트림키}`. OBS: 서버 `rtmp://{서버}/live`, 스트림 키 `{채널ID}?key={스트림키}` | 로컬 검증 A~C, OBS로 확인. 키가 경로가 아니라 query라 시청 주소에 노출되지 않는다 |
| 키 확인 연동 | MediaMTX가 송출 시작·API 호출 때 Spring에 HTTP로 묻는다(`authMethod: http`). Spring은 `action: publish`(스트림 키)와 `action: api`(내부 비밀번호)만 판단하고, 시청(`read`)은 MediaMTX 설정에서 인증 대상에서 뺀다 | 로컬 검증 C·G. API 호출을 인증에 넣은 것은 #26(#10 보안 점검 🟡 1) |
| 키 확인이 응답하지 않으면 | 송출을 거부한다. 진행 중인 방송은 영향 없다 | 로컬 검증 H |
| 재발급 순서 | DB에서 이전 키를 바꾼 **다음** MediaMTX API로 그 채널의 송출 연결을 끊는다 | 로컬 검증 I·J — 반대로 하면 OBS가 2초 만에 이전 키로 다시 붙는다 |
| MediaMTX API | Spring만 내부망으로 부른다. 호스트 포트로 열지 않는다. Spring은 환경변수의 내부 비밀번호를 Basic 인증(사용자 `spring`)으로 싣고, MediaMTX가 그 값을 키 확인 엔드포인트로 물어 Spring이 맞춰 본다 | 연결 목록 응답의 `query`에 키가 그대로 보인다. 같은 내부망의 다른 컨테이너(nginx 등)가 뚫려도 키를 읽거나 송출을 끊지 못하게(#26). 네트워크 분리는 nginx가 HLS 때문에 mediamtx와 같은 망에 있어야 해서 쓸 수 없다 |
| 화질 | 원본 하나. 720p와 자동 전환은 하지 않는다(720p는 서버 측정 뒤 결정, 확정 사양 미해결 1) | 로컬 검증 U~Z |

### 작은 결정 (비교 없이 정함)

| 결정 | 내용 | 이유 |
| --- | --- | --- |
| 패키지 | `com.livestream.channel`(신청·승인·채널·키·제목), `com.livestream.broadcast`(키 확인, 방송 시작·종료, MediaMTX 호출) | 채널 정보와 "지금 송출이 들어오는 상태"는 바뀌는 이유가 다르다 |
| 한 채널 동시 송출 | MediaMTX `overridePublisher: false` | MediaMTX 기본값은 `true`(나중에 들어온 송출이 기존 송출을 밀어낸다). 확정 사양은 두 번째 송출을 거부한다 |
| 키 확인 엔드포인트 위치 | `/internal/` 아래에 두고, nginx는 이 경로를 넘기지 않는다. MediaMTX는 도커 내부망으로 Spring을 직접 부른다. Spring 2대는 같은 내부 이름(`api`)으로 묶는다 | 외부에서 키를 대입해 보는 창구가 RTMP 말고 하나 더 생기면 안 된다. 한 대가 죽어도 키 확인은 다른 대가 받는다 |
| 키 확인에서 거부하는 경우 | 경로가 `live/{채널ID}`가 아님, 채널이 없음, 키가 다름, 채널 주인이 스트리머가 아님 | 확정 사양 5절. 720p 재송출 경로(`720/*`)는 내부 주소에서만 허용(720p를 켤 때) |
| 키 생성 | 보안 난수 32바이트를 URL에 안전한 문자로 만든 문자열 | 추측할 수 없어야 한다. query에 그대로 들어가므로 URL에 안전해야 한다 |
| 신청 동시 처리 | 승인·거절은 "대기 상태일 때만 바꾼다"는 조건부 UPDATE로 한다. 같은 회원의 대기 신청은 하나만(DB 제약) | 운영자가 두 번 누르거나 신청이 두 번 들어와도 한 번만 반영된다 |
| 승인 처리 | 승인 → 역할을 `STREAMER`로 → 채널 생성을 한 트랜잭션으로. 스트림 키는 만들지 않는다 | 중간에 실패하면 "스트리머인데 채널이 없는" 상태가 생긴다. 키를 승인 때 만들면 전체 키를 받는 사람이 운영자뿐이라(C1 — 키는 만든 순간의 응답에만 있다) 스트리머가 볼 수 없다. 키는 스트리머가 스튜디오에서 처음 발급한다 |
| 승인 후 로그인 상태 | 승인 트랜잭션이 끝나면 그 회원의 세션을 모두 지운다(계정 M2의 색인 저장소). 회원은 다시 로그인하면 스트리머로 들어온다 | 세션에는 로그인할 때의 역할(`MEMBER`)이 남아 있다. 세션 안의 인증 객체를 고쳐 쓰는 것보다 단순하다 |
| 방송 제목 | 채널에 둔다(방송 전에 정한 제목 = 다음 방송 제목, 방송 중에 바꾸면 바로 반영). 방송 기록에는 따로 남기지 않는다 | 지난 방송을 보여 주는 기능(VOD)이 없다 |
| 채널 ID | 숫자 일련번호 | 송출 주소·시청 주소에 들어가지만 비밀이 아니다(비밀은 키) |
| 시청 주소 | `/hls/live/{채널ID}/index.m3u8` | 골격의 nginx `/hls/` 설정 그대로 |

| 스트리머 권한 회수 | 확정 사양에서 뺐다 |
| 신청서 내용(사유·심사 메모) | 확정 사양에 없다. 운영자 한 명이 아는 사람만 승인한다 |
| 운영자 화면 | 기획서 B(관리자 페이지). 대기 목록·승인·거절은 화면 없는 API로만 |
| 채널 여러 개, 채널 이미지 업로드 | 확정 사양: 스트리머당 채널 하나, 이미지 없음 |
| 방송 녹화·다시 보기(VOD) | 기획서 B |
| 지난 방송 목록·방송 통계 | VOD가 없으면 보여 줄 게 없다 |
| 방송 예약 | 확정 사양에 없다 |
| 720p 화질 | 서버 CPU 측정 뒤에 정한다(확정 사양 미해결 1). 이번 이슈 범위에 넣지 않는다 |
| 키 확인 외의 송출 통제(송출 중 강제 종료 버튼, 금지어 제목) | 확정 사양에 없다. 키 재발급이 사실상 강제 종료다 |
| CDN | 기획서 B |

## 용어 정의

`docs/result/spec-fixed.md`의 용어 정의를 따른다. 이 도메인에서 쓰는 것:

| 용어 | 뜻 | 쓰지 않는 말 |
| --- | --- | --- |
| 스트리머 신청 | 회원이 스트리머가 되겠다고 요청한 것. 대기·승인·거절 | 권한 요청 |
| 채널 | 스트리머마다 하나 있는 방송 공간 | 방, 룸 |
| 방송 | 송출이 시작돼서 끝날 때까지 한 번 | 라이브, 스트림(방송 뜻으로) |
| 송출 | OBS 등에서 서버로 영상을 보내는 것 | 업로드, 퍼블리시 |
| 스트림 키 | 송출할 때 스트리머임을 증명하는 비밀 문자열 | 방송 키, 송출 키 |
| 스튜디오 | 스트리머가 키·제목·연결 상태를 다루는 화면 | 대시보드 |
| 데모 방송 / 데모 채널 | 서버가 영상 파일로 흉내 내는 방송과 그 채널 | 가짜 방송, 더미 |

## 이 문서에 나온 기술 용어

| 용어 | 한 줄 설명 |
| --- | --- |
| MediaMTX | OBS의 송출(RTMP)을 받아 웹에서 볼 수 있는 HLS로 바꿔 내보내는 미디어 서버 |
| RTMP | OBS가 서버로 영상을 보낼 때 쓰는 프로토콜 |
| HLS | 영상을 짧은 조각 파일로 나눠 HTTP로 보내는 방식. 브라우저가 조각을 차례로 받아 재생한다 |
| 훅 | 어떤 일이 생겼을 때 프로그램이 미리 정해 둔 명령을 실행해 알려 주는 장치 |
| 조건부 UPDATE | "이 조건일 때만 바꾼다"를 SQL 한 문장에 넣어, 동시에 와도 한 번만 바뀌게 하는 방법 |
