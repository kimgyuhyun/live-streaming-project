# PRD — 시청자 활동·방송 목록 (viewer)

> 상태: **확정** (2026-11-26) — V1 A·V2 D와 하지 않을 것을 사용자가 확정했다. 3안 비교 원본은 `docs/result/adr/viewer.md`. 이슈는 #37~#42.
> 규칙(숫자·조건)의 원본은 `docs/result/spec-fixed.md` 7절(시청자 활동)과 9절의 "방송 목록"이다. 9절의 검색과 5절의 썸네일은 이 문서에서 다루지 않는다.
> 시청 세션 동작의 근거는 `docs/spikes/infra-validation.md` 4절이다.

## 개요

시청자가 채널을 팔로우해 두고 다시 찾아오고, 지금 몇 명이 보고 있는지를 방송 화면과 메인 화면의 방송 목록에서 보는 데까지를 다룬다. 메인 화면의 방송 목록은 시청자 수 순으로 줄을 세운다.

이 도메인은 채널 도메인(`prd/channel.md`)의 채널·방송 상태(진행 중 방송) 위에 선다. 시청자 수는 나중에 검색 결과(9절)도 같은 값을 읽는다.

## 사용자 스토리

| # | 스토리 |
| --- | --- |
| 1 | 회원으로서, 마음에 드는 채널을 팔로우하고, 마음이 바뀌면 팔로우를 취소하고 싶다 |
| 2 | 회원으로서, 팔로잉 화면에서 내가 팔로우한 채널 중 지금 방송 중인 채널을 먼저 보고 싶다. 바로 들어가 보려는 것이다 |
| 3 | 시청자(비로그인 포함)로서, 채널 페이지에서 그 채널의 팔로워 수와 지금 보고 있는 사람 수를 보고 싶다 |
| 4 | 시청자(비로그인 포함)로서, 메인 화면에서 지금 방송 중인 방송을 시청자 수가 많은 순으로 훑어보고 싶다 |
| 5 | 스트리머로서, 내 채널을 내가 팔로우해서 팔로워 수가 부풀지 않았으면 한다 |

## 기술 결정

### V1. 동시 시청자 수는 MediaMTX 시청 세션을 모아 센다

**Context** — 확정 사양 7절: 비로그인 포함, 채널 페이지와 메인 방송 목록이 같은 값, 최대 1분 늦게(2026-11-26 10초에서 바꿈). 서버 2대. 시청자가 늘어도 서버 부담이 같이 늘지 않아야 한다(사용자 원칙). 시청자는 영상 조각을 받으려고 이미 MediaMTX에 계속 요청하고, MediaMTX는 시청마다 세션을 만든다(스파이크 1절 T). 세션은 마지막 요청 뒤 약 30초 남고, 쿠키 없는 클라이언트는 요청마다 새 세션을 만든다(4절 AC·AD).

**Decision**
- Spring이 **5초마다** `GET /v3/hlssessions/list`를 마지막 페이지까지 읽어 경로(`live/{채널ID}`)별 세션 수를 센다. 진행 중 방송이 없는 경로는 버린다.
- **IP당 최대 5세션**만 센다(같은 경로 기준). MediaMTX가 진짜 주소를 보도록 nginx `/hls/`가 `X-Forwarded-For`를 넘기고, MediaMTX `hlsTrustedProxies`에 nginx가 있는 도커 대역을 넣는다.
- 서버 2대 중 **한 대만** 센다. Redis 잠금(`SET NX` + 4초 만료)을 잡은 서버가 그 회차를 맡는다. 잡은 서버가 죽으면 잠금이 풀려 다른 서버가 다음 회차를 맡는다.
- 센 결과는 V2의 판(스냅샷)으로 Redis에 쓴다. 읽는 쪽(채널 조회, 방송 목록)은 MediaMTX를 부르지 않는다.
- 세션 목록에서 `remoteAddr`·`path`만 읽는다. 주소는 저장하지 않고 로그에도 남기지 않는다.

**Alternatives**
- B. 채팅 WebSocket 연결 수 — 채팅이 아직 없다. 서버가 죽으면 그 몫을 따로 정리해야 한다.
- C. 방송 화면의 신호(하트비트) — 처음 추천안. 나간 시청자가 10초 안에 빠지고 부풀리기를 막기 쉽지만, 시청자 1,000명에 초당 약 200건으로 시청자 수에 비례해 서버 요청이 는다. 사용자가 서버 부담을 기준으로 버렸다.

**Consequences**
- 시청자가 늘어도 서버 요청은 5초에 한 번(세션 목록 읽기)뿐이다. 읽는 쪽 부담은 시청자 수와 상관없다.
- 나간 시청자는 약 30초 + 5초 뒤에 빠진다(사양 1분 안).
- 영상을 실제로 받는 사람만 센다. 화면만 열고 영상을 멈춘 탭은 세지 않는다. VLC처럼 주소를 직접 여는 클라이언트도 센다.
- 세션 목록이 시청자 수만큼 커진다(세션 1만 개면 수 MB). 집계 한 번 걸린 시간을 로그로 남기고 V2 측정 계획에서 잰다.
- IP당 5세션이라, 한 집(공유기 하나)에서 6명 넘게 보면 5로 센다. 회사·학교 같은 큰 공유 IP는 적게 센다.
- 진짜 주소가 MediaMTX에 닿는지(`hlsTrustedProxies`)는 아직 끝까지 확인하지 않았다. 이슈에서 먼저 확인한다.
- **다시 여는 조건:** 채팅이 생겨 방송 화면이 늘 WebSocket에 붙게 되면, 연결 수(B)와 비교해 정확도·부담을 다시 잰다. 공유 IP 과소 집계 민원이 생기면 IP당 한도를 올린다.

### V2. 방송 목록은 집계가 만든 순위 판(스냅샷)에서 20개씩 꺼낸다

**Context** — 확정 사양 9절: 진행 중 방송만, 시청자 수 많은 순, 같으면 먼저 시작한 순, 20개씩 더 불러온다. 시청자 수는 Redis(V1), 방송·채널은 DB에 있다. 시청자 수는 계속 바뀐다. 사용자 원칙: 문제가 생기면 옮기는 설계가 아니라 처음부터 규모를 감당하는 설계.

**Decision**
- V1 집계가 회차마다 **새 판**을 만든다: `viewers:{판}:rank`(순위 집합 — 값은 `{역순 시작 시각}:{방송ID}`, 점수는 시청자 수), `viewers:{판}:count`(방송ID → 시청자 수). 진행 중 방송은 시청자 0명이어도 판에 넣는다. 두 키를 다 쓴 다음 `viewers:current`를 새 판 번호로 바꾼다. 판은 2분 뒤 만료된다.
- 방송 목록 `GET /api/broadcasts`: 첫 요청은 지금 판에서 0~19번을 꺼내고 응답에 판 번호를 담는다. "더 보기"는 `?snapshot={판}&offset=20`처럼 **같은 판**으로 묻는다. 꺼낸 방송 ID 20개의 제목·채널 이름은 DB에서 한 번에 읽는다(끝난 방송은 거른다).
- 채널 조회의 `viewerCount`는 지금 판의 `count`에서 읽는다(방송 중이 아니면 0).
- 판이 만료됐거나(2분 넘게 머묾) 지금 판이 2분보다 오래됐으면(집계가 멈춤): 목록은 DB의 진행 중 방송을 시작 순으로 주고 시청자 수를 빼고 보낸다.
- 목록 첫 묶음(`snapshot` 없는 요청)은 nginx에서 1초 캐시한다. 회원마다 다른 값이 없다.

**Alternatives**
- A. 진행 중 방송 전부를 읽어 Spring에서 정렬 — 요청마다 진행 중 방송 수에 비례한다. 처음 추천안이었으나 "1,000개에서 느려지면 옮긴다"는 조건부 설계라 사용자가 버렸다.
- B. 신호·종료 때마다 Redis 순위 집합을 고친다 — V1이 신호 방식이 아니라 쓸 일이 없다. 값을 두 곳에 써 어긋날 수 있다.
- C. 시청자 수를 DB에 주기적으로 쓰고 SQL로 정렬 — 5초마다 진행 중 방송 수만큼 DB 쓰기. "더 보기" 사이 순위가 바뀌는 문제는 그대로다.

**Consequences**
- 한 묶음 비용은 진행 중 방송 수와 거의 상관없다(순위 범위 1번 + DB 20개).
- "더 보기"를 해도 같은 판이라 방송이 겹치거나 빠지지 않는다. 대신 판이 만들어진 뒤(최대 5초) 시작된 방송은 다음 첫 요청까지 안 보인다.
- 순위와 수가 한 판에서 같이 만들어져 목록과 채널 페이지 값이 어긋나지 않는다.
- Redis 키가 5초마다 생긴다(2분 만료 → 최대 약 24판). 진행 중 방송 1,000개여도 합쳐 수 MB 안쪽이다.
- 판이 만들어진 뒤 끝난 방송은 DB에서 걸러 한 묶음이 20개보다 적을 수 있다. 화면은 응답의 `hasMore`로 "더 보기"를 판단한다.
- **측정 계획:** 진행 중 방송 100·1,000개, 시청 세션 1,000·10,000개를 흉내 내 (1) 집계 한 번 걸린 시간, (2) 목록 API p95, (3) Redis 메모리를 잰다. 집계가 5초를 넘으면 주기를 늘리고 사양 1분 안인지 다시 본다.
- **다시 여는 조건:** 검색(9절) 결과도 시청자 수 순이므로, 검색을 만들 때 이 판을 그대로 쓸 수 있는지 본다.

### 작은 결정 (비교 없이 정함)

| 결정 | 내용 | 이유 |
| --- | --- | --- |
| 패키지 | `com.livestream.follow`(팔로우·팔로잉), `com.livestream.broadcast`(시청자 수·방송 목록) | 시청자 수와 목록은 진행 중 방송에 묶인다. 팔로우는 방송과 상관없이 채널에 묶인다 |
| 팔로우 저장 | `follow(member_id, channel_id, created_at)`, 기본 키(member_id, channel_id), `channel_id` 색인. 회원·채널 외래 키 | 같은 채널을 두 번 팔로우해도 행은 하나(기본 키). 팔로워 수는 `channel_id` 색인으로 센다 |
| 팔로우 API | `PUT /api/channels/{id}/follow`(팔로우), `DELETE` 같은 주소(취소). 둘 다 멱등이라 204. 자기 채널이면 400(`CANNOT_FOLLOW_OWN_CHANNEL`) | 버튼을 두 번 눌러도 결과가 같다. 확정 사양: 이미 팔로우했어도, 안 했는데 취소해도 오류가 아니다 |
| 내가 팔로우했는지 | 채널 조회 응답에 넣지 않고 `GET /api/channels/{id}/follow`(`{following}`)로 따로 묻는다 | 채널 조회는 nginx가 `$uri`로 1초 캐시한다. 회원마다 다른 값을 넣으면 남의 값이 보인다 |
| 팔로워 수 | `channel.follower_count` 열. 팔로우가 **실제로 새로 들어갔을 때만** `+1`, 취소가 **실제로 지웠을 때만** `−1`을 같은 트랜잭션에서 한다(`UPDATE … SET follower_count = follower_count + 1` — 읽고 더해 쓰지 않는다). 채널 조회 응답에 `followerCount` | 조회 때 세면(`COUNT(*)`) 팔로워가 많은 채널일수록 느려진다(사용자 원칙: 처음부터 감당). 두 번 팔로우·동시 팔로우에도 숫자가 행 수와 같아야 한다 → 동시 팔로우·취소 테스트로 박는다(`defect-repro`) |
| 팔로잉 목록 | `GET /api/me/following?page=`. 방송 중 먼저, 묶음 안에서는 팔로우한 시각 최근 순, 20개씩. SQL 한 번(진행 중 여부는 `ChannelMapper.xml`의 `EXISTS` 식 그대로) | 확정 사양 7절 |
| 비로그인 팔로우 | 화면이 로그인 화면으로 보낸다. API는 401 | 확정 사양 7절 |
| 방송 목록 썸네일 | 썸네일(5절)이 아직 없어 기본 이미지를 보여 준다 | 썸네일은 탐색 도메인에서 만든다 |

## 하지 않을 것

| 하지 않을 것 | 이유 |
| --- | --- |
| 검색(9절) | 이번 이슈 범위 밖. 방송 목록이 쓰는 시청자 수를 그대로 쓰면 된다 |
| 썸네일 생성(5절) | 탐색 도메인에서 다룬다. 목록은 기본 이미지 |
| 사이드바에 팔로잉 채널 목록 | 사용자 결정(2026-11-26): 별도 화면만 |
| 팔로우한 채널 방송 시작 알림 | 기획서 B(알림) |
| 내 채널의 팔로워 목록(누가 팔로우했는지) | 확정 사양에 없다. 수만 보인다 |
| 팔로우 취소 확인 창 | 확정 사양에 없다. 다시 누르면 된다 |
| 스튜디오에 시청자 수 표시 | 이번 요청은 방송 화면·메인 화면. 같은 값을 읽으면 되므로 나중에 붙이기 쉽다 |
| 시청자 수 기록·그래프(최고 시청자 수 등) | 확정 사양에 없다. 지금 값만 센다 |
| 한 사람을 정확히 1로 세기 | 확정 사양: 탭 두 개면 2로 세도 된다 |
| 시청 세션 주소 저장·분석 | 세기만 한다. IP는 집계 중 메모리에서만 쓴다 |
| 나간 시청자를 즉시 빼기 | V1: MediaMTX 세션이 약 30초 남는다. 사양을 1분으로 바꿨다 |

## 용어 정의

`docs/result/spec-fixed.md`의 용어 정의를 따른다. 이 도메인에서 쓰는 것: 팔로우, 팔로우 취소, 팔로워 수, 팔로잉, 동시 시청자 수, 방송, 비로그인 시청자.

| 이 문서에 나온 기술 용어 | 뜻 |
| --- | --- |
| 하트비트(신호) | 화면이 몇 초마다 "아직 보고 있다"고 서버에 알리는 요청(고르지 않은 안) |
| 판(스냅샷) | 한 회차 집계 결과를 통째로 담은 Redis 키 묶음. 번호가 붙고 2분 뒤 사라진다 |
| `hlsTrustedProxies` | MediaMTX가 앞단 프록시(nginx)가 넘긴 `X-Forwarded-For`를 진짜 시청자 주소로 믿게 하는 설정 |
| Redis 정렬 집합 | 값마다 숫자 점수를 붙여 두고, 점수 범위로 지우거나 세는 Redis 자료형 |
| 멱등 | 같은 요청을 두 번 보내도 결과가 한 번 보낸 것과 같은 성질 |
| p95 | 요청 100개 중 느린 쪽 5개를 뺀 가장 느린 응답 시간 |
