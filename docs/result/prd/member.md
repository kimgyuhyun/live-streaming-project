# PRD — 계정 (member)

> 상태: **확정** (2026-11-20) — 기술 결정 4건과 하지 않을 것을 사용자가 확정했다. 3안 비교 원본은 `docs/result/adr/member.md`.
> 규칙(숫자·조건)의 원본은 `docs/result/spec-fixed.md` 2절(회원·계정)과 1절(역할)이다. 이 문서는 그 규칙을 **어떤 구조로, 왜** 만드는지만 적는다.

## 개요

회원 가입, 로그인·로그아웃, 로그인 시도 제한, 계정 정보 변경, 운영자 계정을 다룬다.

이 도메인은 다른 모든 도메인보다 먼저 만든다. 다른 도메인은 "지금 요청한 사람이 누구이고 역할이 무엇인지"를 여기서 받아 쓴다. 특히 **채팅(WebSocket)도 로그인과 같은 세션으로 사람을 확인**하므로, 여기서 정한 인증 방식이 채팅까지 그대로 간다.

## 사용자 스토리

| # | 스토리 |
| --- | --- |
| 1 | 비로그인 시청자로서, 이메일·비밀번호·닉네임만으로 가입하고 싶다. 채팅을 쓰고 후원하려면 회원이어야 하기 때문이다 |
| 2 | 회원으로서, 로그인하면 일주일 동안은 다시 로그인하지 않고 쓰고 싶다. 방송을 볼 때마다 로그인하는 건 번거롭다 |
| 3 | 회원으로서, 누가 내 비밀번호를 계속 넣어 봐도 계정이 털리지 않았으면 한다 |
| 4 | 회원으로서, 닉네임과 비밀번호를 바꾸고 싶다. 비밀번호를 바꾸면 다른 기기에서는 로그아웃되어야 한다. 비밀번호가 샜을 때 바꾸는 것만으로 막혀야 하기 때문이다 |
| 5 | 운영자로서, 서비스를 띄우면 내 계정이 이미 있어서 바로 스트리머 신청을 승인할 수 있으면 한다 |
| 6 | (다른 도메인으로서) 요청한 사람이 비로그인인지, 회원·스트리머·운영자 중 무엇인지 알고 싶다. 채팅 쓰기·후원·스튜디오는 역할에 따라 막아야 한다 |

## 기술 결정

### M1. 인증은 Spring Security로, 로그인은 컨트롤러에서 한다

**Context** — 로그인하면 세션에 "누구, 무슨 역할"을 싣고, 이후 요청마다 권한을 검사해야 한다. 로그인 시도 제한은 비밀번호 비교 **전에** 들어가야 하고, 채팅 WebSocket도 같은 세션으로 사람을 확인한다. 모든 도메인의 권한 검사가 이 틀을 따르므로 나중에 바꾸면 컨트롤러·테스트를 전부 고친다.

**Decision** — 권한 검사·세션 저장은 Spring Security(Spring의 인증·권한 프레임워크)에 맡긴다. 로그인은 컨트롤러 → 서비스에서 직접 처리한다: 시도 횟수를 센다 → 막혔으면 거부 → 비밀번호 비교 → 성공하면 횟수 초기화 → 세션 ID 교체 → `SecurityContextRepository`로 세션에 저장. 경로별 권한은 보안 설정 한 곳에 모은다. OTT `EmailAuthController`·`SecurityConfig`를 가져온다.

**Alternatives**
- B. Spring Security 필터로 로그인까지 처리 — 시도 제한을 세는 곳·초기화하는 곳·실패 처리가 필터와 핸들러로 흩어져 순서를 테스트로 묶기 어렵다. OTT 코드를 쓰지 못한다.
- C. Spring Security 없이 인터셉터로 직접 — 권한 검사·세션 고정 방어·테스트 도구(가짜 로그인 사용자)를 직접 만들어야 한다. OTT 코드를 쓰지 못한다.

**Consequences**
- 로그인 순서가 서비스 메서드 하나에 있어 테스트 시나리오로 그대로 옮긴다. 컨트롤러는 `@WebMvcTest` + `spring-security-test`로 역할별 검사를 한다.
- 세션 ID 교체와 세션 저장을 직접 불러야 한다(B는 자동). 빠뜨리면 세션 고정 공격(공격자가 미리 정한 세션 ID로 피해자를 로그인시키는 공격)에 열린다 — "로그인 전후 세션 ID가 다르다"를 테스트로 박는다.
- Spring Security 설정이 커서 처음 읽기 어렵고, 필터 순서 문제는 디버깅이 번거롭다.
- **다시 여는 조건:** 소셜 로그인(B)을 넣게 되면 OAuth2 로그인이 필터 방식이라 B 쪽 구조와 섞인다. 그때 로그인 경로 구조를 다시 본다.

### M2. 다른 기기 로그아웃은 Spring Session 색인 저장소로 한다

**Context** — 확정 사양: 비밀번호를 바꾸면 다른 기기의 로그인이 풀린다. Spring Session Redis 기본 저장소(`repository-type: default`)는 세션 ID로만 찾을 수 있어 "이 회원의 세션 전부"를 모른다.

**Decision** — `spring.session.redis.repository-type: indexed`로 회원별 색인을 함께 저장한다. 비밀번호를 바꾸면 그 회원의 세션 목록을 찾아(`FindByIndexNameSessionRepository`) 지금 쓰는 세션만 남기고 지운다.

**Alternatives**
- B. 세션 버전 비교(회원 테이블에 버전 숫자, 요청마다 비교) — 로그인한 요청마다 회원의 버전을 읽어야 한다. 비밀번호를 바꾸는 일은 드문데 비용은 모든 요청이 낸다.
- C. 회원별 세션 ID 집합을 직접 관리 — Spring Session이 이미 하는 일을 다시 만든다. 만료된 세션 ID를 집합에서 청소하는 일까지 생긴다.

**Consequences**
- 비밀번호를 바꿀 때만 일한다. 평소 요청에는 비용이 없다.
- Redis에 세션당 키가 몇 개 더 생긴다(색인·만료 추적). 이 규모에서는 무시할 만하다.
- Redis 키 만료 알림(`notify-keyspace-events`)에 기댄다. Spring Session이 시작할 때 켠다.
- 이미 열린 채팅 WebSocket은 세션이 지워져도 바로 끊기지 않는다 — 채팅 PRD에서 다룬다.
- **다시 여는 조건:** Redis에서 `CONFIG` 명령을 쓸 수 없는 환경(관리형 Redis 등)으로 옮기면 B로 바꾼다.

### M3. 로그인 실패 횟수는 Redis에, 비밀번호 비교 전에 센다

**Context** — 확정 사양: 같은 이메일 5번 연속 실패 → 15분 차단(마지막 실패 후 15분 동안 실패가 없으면 0으로), 같은 IP 15분 안에 20번 실패 → 15분 차단. Spring이 2대이고 nginx가 요청을 번갈아 보낸다. 동시에 들어온 실패도 정확히 세야 한다.

**Decision** — 이메일별(소문자로 맞춘 이메일)·IP별 카운터를 Redis에 둔다. 로그인 요청이 오면 **비밀번호를 비교하기 전에** 두 카운터를 먼저 원자적으로 1 올리고, 상한을 넘었으면 비교하지 않고 거부한다. 증가와 만료 설정은 Lua 스크립트(Redis 안에서 한 번에 실행되는 작은 프로그램) 하나로 실행한다. 로그인에 성공하면 이메일 카운터를 지운다.
- 이메일 카운터: 증가할 때마다 만료를 15분으로 **다시 잡는다**(마지막 실패 기준).
- IP 카운터: 첫 실패에만 만료 15분을 잡는다(고정 구간). 사양이 "15분 안에 20번"이기 때문이다.
- 차단 중이면 남은 시간(카운터의 남은 만료)을 응답에 담는다.

**Alternatives**
- B. DB(Oracle) 테이블 — 공격 중에는 실패마다 DB 쓰기가 몰리고, 오래된 행을 지우는 작업이 따로 필요하다.
- C. 서버 메모리 — 서버 2대가 따로 세서 사실상 10번까지 허용된다. 재시작하면 횟수가 사라진다.

**Consequences**
- 서버 2대가 같은 횟수를 본다. 동시 요청에서도 상한이 지켜진다 — "동시에 N개 실패 요청을 보내도 비밀번호 비교는 상한까지만 일어난다"를 통합 테스트로 박는다(OTT `LoginAttemptLimitTest` 방식).
- 비교 전에 세므로, **성공한 로그인도 일단 1을 센 뒤 지운다.**
- 남의 이메일로 5번 틀려서 그 사람을 15분 막을 수 있다. 확정 사양이 받아들인 동작이다(IP 기준 제한이 같은 IP의 반복은 막는다).
- Redis가 죽으면 카운터를 못 쓰지만, 세션도 Redis라 어차피 로그인이 안 된다. 따로 처리하지 않는다.
- **다시 여는 조건:** 특정 계정을 노린 차단 공격이 실제로 관측되면, 이메일 기준 차단 대신 사람 확인(캡차)을 요구하는 방식(OTT 방식)을 검토한다.

### M4. 운영자 계정은 앱 시작 때 환경변수로 만든다

**Context** — 확정 사양: 운영자 계정은 가입으로 만들지 않고 배포할 때 미리 넣어 둔다. 운영자 비밀번호(또는 해시)가 git에 남으면 안 된다.

**Decision** — 앱이 시작할 때 `OPERATOR_EMAIL`·`OPERATOR_PASSWORD` 환경변수가 둘 다 있으면, 그 이메일의 계정이 없을 때만 역할 `OPERATOR`로 만든다. 이미 있으면 아무것도 하지 않는다. 값은 `.env`에 두고 `.env.example`에는 키만 적는다.

**Alternatives**
- A. Flyway 마이그레이션에 `INSERT` — 비밀번호 해시가 git에 남고, 바꾸려면 마이그레이션을 또 커밋한다. 테스트 DB에도 운영자가 생긴다.
- C. 배포 후 손으로 `INSERT` — 비밀은 안 남지만 DB를 새로 만들 때마다 사람이 해야 하고, 테스트할 코드가 없다.

**Consequences**
- 환경마다 `.env`로 다르게 둘 수 있다. 테스트에서는 비워 두면 운영자가 생기지 않는다.
- 서버 2대가 동시에 시작하면 둘 다 만들려고 한다. 이메일 UNIQUE 제약으로 하나만 성공하고, 실패한 쪽은 "이미 있음"으로 보고 넘어간다 — 통합 테스트로 박는다.
- `.env`의 비밀번호를 바꿔도 이미 있는 계정은 바뀌지 않는다. 운영자도 일반 비밀번호 변경 기능을 쓴다.
- **다시 여는 조건:** 운영자가 둘 이상 필요해지면(B인 관리자 페이지와 함께) 운영자 관리 방식을 다시 정한다.

### 기획서에서 이미 정한 것 (비교 없이 옮김)

| 결정 | 내용 | 근거 |
| --- | --- | --- |
| 세션 + 쿠키 | 로그인 상태는 Spring Session(세션을 서버 메모리가 아니라 외부 저장소에 두는 라이브러리)으로 Redis에 저장한다. 브라우저에는 세션 식별자만 쿠키로 준다. 유휴 7일 | 기획서 기술 스택 — JWT는 WebSocket 인증을 따로 만들어야 해서 쓰지 않는다. 서버 2대가 같은 세션을 본다 |
| 위조 요청 방어 | 상태를 바꾸는 요청(POST·PUT·PATCH·DELETE)은 출처(`Origin`, 없으면 `Referer`)가 우리 도메인일 때만 받는다. 세션 쿠키는 `HttpOnly`, `SameSite=Lax` | 기획서 기술 스택 — OTT의 출처 검증 필터를 가져온다. CSRF 토큰(요청마다 서버가 준 비밀값을 함께 보내게 하는 방식)은 쓰지 않는다 |

### 작은 결정 (비교 없이 정함)

| 결정 | 내용 | 이유 |
| --- | --- | --- |
| 비밀번호 해시 | BCrypt(일부러 느리게 만든 해시. 비밀번호를 하나씩 대입해 보는 데 오래 걸리게 한다) | Spring Security 기본값. 다른 선택지와 차이가 이 규모에서 의미 없다 |
| 없는 이메일로 로그인 | 비밀번호 비교를 가짜 해시로 한 번 한다 | 비교를 건너뛰면 응답이 빨라져서 "이 이메일은 없다"가 응답 시간으로 드러난다 |
| 이메일 대소문자 | 소문자로 바꿔 저장하고 UNIQUE 제약을 건다 | 확정 사양: 대소문자를 구분하지 않는다. 저장할 때 맞추면 조회·제약이 단순하다 |
| 닉네임 중복 | UNIQUE 제약. 가입·변경이 동시에 들어와도 DB가 막는다 | 앱에서 먼저 조회만 하면 동시 요청 둘이 모두 통과한다 |
| 역할 | 회원 한 명에 역할 하나: `MEMBER` → `STREAMER`(승인되면), `OPERATOR`(미리 넣음) | 스트리머는 회원의 모든 것을 할 수 있다. 역할을 여러 개 갖는 경우가 없다 |
| 실제 사용자 IP | nginx가 넘긴 주소를 Spring이 그대로 믿게 설정한다(`server.forward-headers-strategy: native`) | 로그인 시도 제한(IP 기준)이 nginx 주소가 아니라 사용자별로 걸려야 한다 |
| DB 마이그레이션 도구 | Flyway(테이블 변경을 번호 붙은 SQL 파일로 관리하는 도구) 11.7.2(Spring Boot 3.5.16이 정한 버전)를 그대로 쓴다. "테스트한 Oracle은 21.3까지" 경고는 남긴다 | 로컬 검증에서 Oracle 23.26에 적용이 됐다. 13.x로 올리면 Spring Boot가 맞춰 둔 버전을 벗어난다. **다시 여는 조건:** Flyway 때문에 마이그레이션이 Oracle에서 실패하면 버전을 올리거나 SQL 직접 관리로 바꾼다 |

## 하지 않을 것

| 하지 않을 것 | 이유 |
| --- | --- |
| 이메일 인증(가입 확인 메일) | 메일 발송 인프라가 필요하다. 3주 범위 밖 (확정 사양) |
| 비밀번호 찾기(재설정 메일) | 위와 같다 |
| 회원 탈퇴 | 후원 원장이 회원을 참조한다. 탈퇴 후 원장 처리를 정하는 일이 범위를 넘는다 (확정 사양) |
| 소셜 로그인 | 기획서 B(추후 확장) |
| 스트리머 권한 회수 | 확정 사양에서 뺐다. 스트리머 신청·승인 자체는 채널 도메인에서 다룬다 |
| 관리자 페이지(회원 목록·제재) | 기획서 B. 운영자는 화면 없는 API만 쓴다 |
| 사람 확인(캡차) | OTT에는 있지만 확정 사양에 없다. 로그인 시도 제한으로 충분하다 |
| 로그인 기록·감사 로그 | 기획서 B(상세 감사 로그) |

| 회원 | 이메일로 가입한 사람 | 유저, 사용자(코드에서) |
| 비로그인 시청자 | 로그인하지 않은 방문자 | 게스트, 익명 |
| 스트리머 | 운영자가 승인한 회원 | BJ, 크리에이터 |
| 운영자 | 스트리머 신청을 승인하는 사람(본인) | 관리자 |
| 로그인 시도 제한 | 로그인 실패가 쌓이면 잠시 로그인을 막는 것 | 계정 잠금 |

## 이 문서에 나온 기술 용어

| 용어 | 한 줄 설명 |
| --- | --- |
| Spring Session | 세션을 서버 메모리가 아니라 Redis 같은 외부 저장소에 두는 라이브러리 |
| CSRF 토큰 | 요청마다 서버가 준 비밀값을 함께 보내게 해서 위조 요청을 막는 방식 |
| BCrypt | 일부러 느리게 만든 비밀번호 해시 |
| Flyway | 테이블 변경을 번호 붙은 SQL 파일로 관리하는 도구 |
