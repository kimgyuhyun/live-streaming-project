## M1. 인증을 어떤 틀로 만드는가

**풀려는 것:** 로그인하면 세션에 "누구, 무슨 역할"을 싣고, 이후 요청마다 그걸 꺼내 권한을 검사한다. 로그인 시도 제한을 비밀번호 비교 **전에** 끼워 넣어야 하고, 채팅 WebSocket 연결도 같은 세션으로 사람을 확인해야 한다.

| 안 | 요약 |
| --- | --- |
| **A. Spring Security + 컨트롤러에서 로그인** | 권한 검사·세션 저장·세션 고정 공격 방어는 Spring Security에 맡긴다. 로그인 자체는 컨트롤러 → 서비스에서 직접 처리하고(시도 제한 → 비밀번호 비교 → 세션에 저장), 결과를 Spring Security의 저장소로 세션에 싣는다. **OTT와 같은 방식** |
| B. Spring Security 필터로 로그인까지 | 로그인도 Spring Security 필터(JSON을 읽는 커스텀 인증 필터 + 성공·실패 핸들러)로 처리한다. 컨트롤러에 로그인 코드가 없다 |
| C. Spring Security 없이 직접 | 인터셉터(컨트롤러 앞에서 요청을 가로채는 Spring MVC 장치)가 세션의 회원 ID·역할을 읽어 권한을 검사한다. 비밀번호 해시는 `spring-security-crypto`(해시 부분만 떼어 낸 라이브러리)만 쓴다 |

| 기준 | A | B | C |
| --- | --- | --- | --- |
| 1. 데이터 구조 | 세션에 `SecurityContext`(인증 결과 객체). 회원 테이블은 셋 다 같다 | A와 같다 | 세션에 회원 ID·역할 속성 두 개 |
| 2. API 변경지점 | `POST /api/auth/login`·`logout`이 일반 컨트롤러. 권한은 설정 한 곳(`authorizeHttpRequests`) + 필요하면 메서드 단위 | 로그인 경로는 필터가 받아 컨트롤러가 없다. 응답 형식을 핸들러에서 따로 만든다 | 로그인은 일반 컨트롤러. 권한은 인터셉터 + 직접 만든 어노테이션 |
| 3. 상태관리 | 해당 없음 (프론트는 세 안 모두 쿠키만 들고 있다) | 해당 없음 | 해당 없음 |
| 4. 핵심 동작: 시도 제한 → 비교 순서 | 서비스 메서드 하나에 순서대로 있다(센다 → 막혔으면 거부 → 비교 → 성공 시 초기화) | 세는 곳(필터 앞)·초기화하는 곳(성공 핸들러)·실패 처리(실패 핸들러)가 흩어진다 | A와 같이 서비스 하나에 있다 |
| 4. 핵심 동작: 세션 고정 방어 | 로그인 때 세션 ID 교체(`changeSessionId`)를 직접 부른다. OTT에 있다 | Spring Security가 자동으로 한다 | 직접 부른다 |
| 4. 핵심 동작: WebSocket | 핸드셰이크(연결을 처음 맺는 HTTP 요청) 때 세션의 인증 정보를 그대로 읽는다 | A와 같다 | 세션 속성을 직접 읽는다 |
| 5. 컴포넌트 | 해당 없음 | 해당 없음 | 해당 없음 |
| 6. 기존 패턴 | OTT `EmailAuthController`·`SecurityConfig`·`OriginValidationFilter`를 거의 그대로 가져온다 | OTT와 다르다. 새로 짠다 | OTT 코드를 가져오지 못한다. 출처 검증 필터만 서블릿 필터로 옮긴다 |
| 7. 테스트 용이성 | 서비스는 Spring 없이 단위 테스트. 컨트롤러는 `@WebMvcTest` + `spring-security-test`(가짜 로그인 사용자를 넣어 주는 도구)로 역할별 검사 | 로그인 흐름을 필터 단위로 테스트해야 해서 단위 테스트가 어렵다 | 단순하지만 권한 검사 테스트 도구를 직접 만든다 |

**추천: A.** OTT 코드를 가져올 수 있고, 시도 제한 → 비교 → 세션 저장이 한 서비스 메서드에 순서대로 있어 테스트 시나리오로 옮기기 쉽다.
**A를 고르면 감수하는 것:** Spring Security 설정이 커서 처음 읽는 사람에게 어렵다. 세션 고정 방어·컨텍스트 저장을 직접 불러야 해서(B는 자동) 빠뜨리면 구멍이 된다 — 테스트로 잡는다. 필터 체인 순서 문제는 디버깅이 번거롭다.

## M2. 비밀번호를 바꾸면 다른 기기의 로그인을 어떻게 풀까

**풀려는 것:** 확정 사양 — 비밀번호를 바꾸면 다른 기기의 로그인이 풀린다. Spring Boot 3.5의 Spring Session Redis 기본 저장소(`repository-type: default`)는 세션 ID로만 찾을 수 있어서 "이 회원의 세션 전부"를 모른다.

| 안 | 요약 |
| --- | --- |
| **A. 색인 저장소** | `spring.session.redis.repository-type: indexed`. Spring Session이 회원 이름별 색인을 함께 저장한다. 비밀번호를 바꾸면 그 회원의 세션 목록을 찾아 지금 세션만 빼고 지운다 |
| B. 세션 버전 비교 | 회원 테이블에 `credential_version`(비밀번호를 바꿀 때마다 1 올리는 숫자)을 둔다. 로그인 때 세션에 그 값을 넣고, **요청마다** DB 값과 비교해서 다르면 세션을 버린다 |
| C. 회원별 세션 목록 직접 관리 | 로그인할 때 Redis에 `회원ID → 세션ID 집합`을 직접 쌓는다. 비밀번호를 바꾸면 그 집합의 세션을 지운다 |

| 기준 | A | B | C |
| --- | --- | --- | --- |
| 1. 데이터 구조 | Redis에 세션 외에 색인 키·만료 추적 키가 더 생긴다 | 회원 테이블 컬럼 하나 + 세션 속성 하나 | Redis 집합 키 하나(회원당). 만료된 세션 ID가 집합에 남는다 |
| 2. API 변경지점 | 비밀번호 변경 서비스에서 세션 저장소를 부른다 | 모든 요청 앞에 비교하는 필터가 생긴다 | 로그인·로그아웃·비밀번호 변경 세 곳에서 집합을 고친다 |
| 3. 상태관리 | 해당 없음 | 해당 없음 | 해당 없음 |
| 4. 핵심 동작: 비용 | 비밀번호를 바꿀 때만 일한다 | **로그인한 요청마다** 회원의 버전을 읽는다(DB 또는 캐시) | 바꿀 때만 일한다. 대신 집합 청소를 따로 해야 한다 |
| 4. 핵심 동작: 의존 | Redis의 키 만료 알림(`notify-keyspace-events`) 설정이 필요하다. Spring Session이 시작할 때 켜 준다 | Redis 설정과 무관 | Redis 설정과 무관 |
| 5. 컴포넌트 | 해당 없음 | 해당 없음 | 해당 없음 |
| 6. 기존 패턴 | 세션을 Spring Session에 맡기는 기획서 결정과 맞다. OTT에는 이 기능이 없다 | OTT에 없다 | OTT에 없다. Spring Session이 이미 하는 일을 다시 만든다 |
| 7. 테스트 용이성 | Testcontainers Redis로 "세션 두 개 → 변경 → 하나만 남음" 통합 테스트 | 필터 단위 테스트가 쉽다 | 집합 청소까지 테스트해야 한다 |

**추천: A.** 바꿀 때만 일하고, 이미 있는 기능을 설정으로 켠다.
**A를 고르면 감수하는 것:** Redis에 키가 세션당 몇 개 더 생긴다(이 규모에서 무시할 만하다). Redis 키 만료 알림에 기대므로, 그 설정을 막아 둔 관리형 Redis로 옮기면 동작하지 않는다 — **다시 여는 조건:** Redis에서 `CONFIG` 명령을 쓸 수 없게 되면 B로 바꾼다.
**세 안 모두 같은 한계:** 이미 열려 있는 채팅 WebSocket은 세션이 지워져도 바로 끊기지 않는다. 채팅 도메인 PRD에서 다룬다.

## M3. 로그인 실패 횟수를 어디에 세는가

**풀려는 것:** 확정 사양 — 같은 이메일 5번 연속 실패 → 15분 차단, 성공하면 초기화. 같은 IP 15분 안에 20번 실패 → 15분 차단. Spring이 2대이고, 동시에 들어온 실패도 정확히 세야 한다.

| 안 | 요약 |
| --- | --- |
| **A. Redis 카운터** | 이메일별·IP별 키를 Redis에 둔다. **비밀번호를 비교하기 전에** 먼저 1을 더하고(원자적), 상한을 넘었으면 비교하지 않고 거부한다. 성공하면 이메일 카운터를 지운다. **OTT 방식** |
| B. DB(Oracle) | 이메일별·IP별 실패 기록 테이블을 둔다. `UPDATE … SET count = count + 1`로 센다 |
| C. 서버 메모리 | 각 Spring 서버 메모리에 센다(Caffeine 같은 로컬 캐시) |

| 기준 | A | B | C |
| --- | --- | --- | --- |
| 1. 데이터 구조 | Redis 키 몇 개, 만료 시간이 붙어 자동으로 사라진다 | 테이블 1~2개, 오래된 행을 지우는 작업이 따로 필요하다 | 서버마다 따로 |
| 2. API 변경지점 | 로그인 서비스 안 | 로그인 서비스 안 | 로그인 서비스 안 |
| 3. 상태관리 | 해당 없음 | 해당 없음 | 해당 없음 |
| 4. 핵심 동작: 서버 2대 | 같은 Redis를 보니 한 번에 센다 | 같은 DB를 보니 한 번에 센다 | **nginx가 번갈아 보내서 서버마다 따로 센다. 사실상 10번까지 허용된다** |
| 4. 핵심 동작: 동시 요청 | Redis 증가가 원자적이라 정확하다 | 행 잠금으로 정확하지만, 공격 중에는 실패마다 DB 쓰기가 몰린다 | 서버 안에서는 정확, 서버 사이는 틀린다 |
| 4. 핵심 동작: 저장소가 죽으면 | 세션도 Redis에 있으므로 어차피 로그인이 안 된다. 따로 고민할 일이 없다 | DB가 살아 있으면 동작 | 재시작하면 횟수가 사라진다 |
| 5. 컴포넌트 | 해당 없음 | 해당 없음 | 해당 없음 |
| 6. 기존 패턴 | OTT `LoginAttemptService`·`RedisCounterUtil`을 가져온다 | OTT와 다르다 | OTT와 다르다 |
| 7. 테스트 용이성 | Testcontainers Redis로 동시 요청 테스트(OTT `LoginAttemptLimitTest`와 같은 방식) | Testcontainers Oracle로 가능, 느리다 | 쉽지만 서버 2대 문제를 테스트로 드러내기 어렵다 |

**추천: A.**
**A를 고르면 감수하는 것:** Redis 키 만료로 횟수가 사라지므로 "몇 분 동안의 실패를 세는가"가 만료 시간에 묶인다(아래 확인 필요). 이메일 문자열이 키에 들어가므로 키는 소문자로 맞춘 이메일로 만든다. 공격자가 남의 이메일로 5번 틀려서 그 사람을 15분 막을 수 있다 — 확정 사양이 받아들인 동작이다.

### 확인 필요 — "5번 연속 실패"의 시간 범위

확정 사양에는 이메일 기준 실패를 **얼마 동안** 세는지가 없다("연속", "성공하면 초기화"만 있다). A안은 카운터에 만료 시간을 붙여야 하므로 이 값이 필요하다.

| 해석 | 동작 | 문제 |
| --- | --- | --- |
| 기간 없음 | 어제 4번 틀리고 오늘 1번 틀려도 차단 | 카운터를 영원히 들고 있어야 한다. 사용자도 이해하기 어렵다 |
| OTT 방식(고정 구간) | 첫 실패부터 15분 안에 5번이면 차단, **차단은 첫 실패 기준 15분 뒤에 풀린다** | 5번째 실패가 14분째였다면 1분만 막힌다. "15분 동안 차단"과 어긋난다 |
| **제안: 마지막 실패 기준** | 실패할 때마다 만료를 15분으로 다시 잡는다. 5번째 실패 순간부터 15분 동안 차단, 마지막 실패 후 15분 동안 실패가 없으면 0으로 돌아간다 | 확정 사양 문장("5번 연속 실패하면 15분 동안")과 그대로 맞는다 |

제안대로 하면 확정 사양 2절에 "마지막 실패 후 15분 동안 실패가 없으면 실패 횟수는 0으로 돌아간다"를 한 줄 추가한다. IP 기준(15분 안에 20번)은 사양에 기간이 있어서 그대로다.

→ **제안대로 확정**(2026-11-20). 확정 사양 2절에 추가했다.

## M4. 운영자 계정을 어떻게 미리 넣는가

**풀려는 것:** 확정 사양 — 운영자 계정은 가입으로 만들지 않고 배포할 때 미리 넣어 둔다. 운영자 비밀번호(또는 그 해시)가 git에 남으면 안 된다.

| 안 | 요약 |
| --- | --- |
