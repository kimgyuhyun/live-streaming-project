## C1. 스트림 키를 어떻게 저장하나

**풀려는 것:** 확정 사양 — 키 전체는 발급·재발급 직후 한 번만 보여 주고 그 뒤로는 앞 4자리만, 재발급하면 이전 키는 즉시 무효, 키는 로그·응답·화면에 전체가 나오지 않는다. 송출 시작 때 MediaMTX가 넘긴 키(`query`)와 맞는지 확인해야 한다.

| 안 | 요약 |
| --- | --- |
| **A. 해시 + 앞 4자리** | 키의 SHA-256 해시(되돌릴 수 없는 고정 길이 값)와 앞 4자리만 저장한다. 확인할 때는 들어온 키를 해시해서 비교한다 |
| B. 평문 | 키를 그대로 저장한다. 확인은 문자열 비교, 앞 4자리는 잘라서 보여 준다 |
| C. 암호화 | 키를 서버 비밀키로 암호화해 저장한다. 필요하면 풀어서 다시 보여 줄 수 있다 |

| 기준 | A | B | C |
| --- | --- | --- | --- |
| 1. 데이터 구조 | 채널에 `stream_key_hash`, `stream_key_prefix` | 채널에 `stream_key` | 채널에 `stream_key_encrypted` + 서버 비밀키(환경변수) |
| 2. API 변경지점 | 발급·재발급 응답에만 전체 키. 조회 API는 앞 4자리만 | 같다(조회에서 잘라야 한다) | 같다 |
| 3. 상태관리 | 해당 없음 | 해당 없음 | 해당 없음 |
| 4. 핵심 동작: DB가 새면 | 키를 알아낼 수 없다 | **모든 채널로 송출할 수 있다** | 서버 비밀키까지 새지 않으면 안전 |
| 4. 핵심 동작: 확인 비용 | 해시 한 번(아주 빠르다). 키가 32바이트 난수라 BCrypt처럼 느린 해시가 필요 없다 | 문자열 비교 | 복호화 한 번 |
| 4. 핵심 동작: "한 번만 보여 준다" | 저장된 값으로 다시 보여 줄 수 없으니 저절로 지켜진다 | 코드로 지켜야 한다(실수로 응답에 넣기 쉽다) | 코드로 지켜야 한다 |
| 5. 컴포넌트 | 해당 없음 | 해당 없음 | 해당 없음 |
| 6. 기존 패턴 | 계정의 비밀번호를 해시로만 저장하는 것(M1 작은 결정)과 같은 원칙 | 다르다 | 비밀키 관리가 새로 생긴다 |
| 7. 테스트 용이성 | "저장된 값으로 원래 키를 만들 수 없다", "앞 4자리만 응답" 단위 테스트가 쉽다 | 같다 | 비밀키를 테스트마다 넣어야 한다 |

**추천: A.**
**A를 고르면 감수하는 것:** 키를 잃어버리면 다시 볼 수 없고 재발급해야 한다(확정 사양과 같다). 데모 방송처럼 서버 밖에서 키를 써야 하는 쪽은 발급 순간의 응답을 받아 따로 보관해야 한다 — C3과 이어진다. 비교는 시간 차이로 정보가 새지 않게 일정 시간 비교(`MessageDigest.isEqual`)를 쓴다.

## C2. 방송이 시작·종료된 걸 서버가 어떻게 아나

**풀려는 것:** 송출이 들어오면 "방송 중"이 되고, 끊기면 "방송 종료"가 되어야 한다. 채널 페이지·스튜디오 연결 상태·방송 목록·채팅(방송 중일 때만)·후원(방송 중인 채널에만)이 이 상태를 읽는다. 키 확인 요청(C1)은 "송출해도 되나"만 묻는 것이라, 확인을 통과해도 실제로 영상이 들어온다는 보장은 없다.

| 안 | 요약 |
| --- | --- |
| A. MediaMTX 훅만 | 방송이 준비되면(`runOnAvailable`) / 끊기면(`runOnUnavailable`) MediaMTX가 명령을 실행해 Spring 내부 주소로 알린다 |
| B. Spring이 주기적으로 조회만 | Spring이 몇 초마다 MediaMTX API(`/v3/paths/list`)를 불러, 지금 송출 중인 경로와 DB의 방송 상태를 맞춘다 |
| **C. 훅 + 주기적 대조** | 평소에는 훅으로 즉시 반영하고, 1분마다 MediaMTX API와 대조해서 놓친 알림을 고친다 |

| 기준 | A | B | C |
| --- | --- | --- | --- |
| 1. 데이터 구조 | 방송 테이블(채널, 시작 시각, 종료 시각). 셋 다 같다 | 같다 | 같다 |
| 2. API 변경지점 | Spring에 내부 알림 엔드포인트 2개(시작·종료) | 내부 엔드포인트 없음. 조회 작업 하나 | 알림 엔드포인트 2개 + 대조 작업 하나 |
| 3. 상태관리 | 해당 없음 | 해당 없음 | 해당 없음 |
| 4. 핵심 동작: 반영 지연 | 거의 즉시 | 조회 간격만큼(예: 5초) | 거의 즉시 |
| 4. 핵심 동작: 알림을 놓치면 | **방송이 끝났는데 계속 "방송 중"으로 남는다.** MediaMTX가 재시작되거나, 알림 순간 Spring이 둘 다 죽어 있으면 생긴다 | 다음 조회에서 저절로 맞는다 | 최대 1분 뒤 대조가 고친다 |
| 4. 핵심 동작: 서버 2대 | 알림은 한 대만 받는다 | **두 대가 같이 조회한다** → 같은 방송을 두 번 시작 처리하지 않게 DB 제약이나 한 대만 돌게 하는 장치가 필요하다 | 대조 작업에서 B와 같은 문제가 있다. 단 1분 간격이라 DB 제약(채널당 진행 중 방송 하나)으로 충분하다 |
| 4. 핵심 동작: 미디어 서버 이미지 | 훅 명령에 `wget`이 필요하다 → 지금 이미지(셸 없음)를 `-ffmpeg` 이미지로 바꾼다 | 이미지 그대로 | A와 같다 |
| 5. 컴포넌트 | 해당 없음 | 해당 없음 | 해당 없음 |
| 6. 기존 패턴 | 검증에서 훅(`runOnAvailable`)으로 720p 변환을 띄워 봤다 | 검증에서 API 목록 조회를 써 봤다 | 둘 다 써 봤다 |
| 7. 테스트 용이성 | 알림 엔드포인트는 단위 테스트 쉬움. 놓친 알림은 테스트할 방법이 없다 | 조회·대조 로직을 가짜 MediaMTX 응답으로 단위 테스트 | 둘 다 + "알림 없이 대조만으로 고쳐진다" 테스트 |

**추천: C.**
**C를 고르면 감수하는 것:** 시작·종료를 처리하는 길이 두 개(알림, 대조)라 둘이 같은 결과를 내도록 같은 처리 함수를 쓰고 멱등(같은 알림을 두 번 받아도 결과가 같게)으로 만든다. 미디어 서버 이미지를 `-ffmpeg`로 바꿔 이미지가 커진다(720p를 켜면 어차피 필요하다). 훅이 Spring을 부를 때 실패하면 다시 시도하지 않고 대조에 맡긴다.

## C3. 데모 방송의 스트리머 계정과 키를 어떻게 준비하나

**풀려는 것:** 확정 사양 10절 — 테스트 스트리머 계정 3~5개가 서버 안에서 영상 파일을 반복 송출한다. 데모도 실제 방송과 같은 경로(키 확인 → 수신 → 시청)를 타고, 데모 스트리머는 "본인이 승인한 테스트 계정"이다. C1에서 A를 고르면 서버에는 키의 해시만 있어서, 시뮬레이터가 쓸 원래 키를 서버에서 꺼낼 수 없다.

| 안 | 요약 |
| --- | --- |
| A. 앱 시작 때 환경변수로 만들기 | `.env`에 데모 계정 수와 키를 적어 두면, 앱이 시작할 때 데모 스트리머·채널을 바로 만들고 그 키의 해시를 저장한다(계정 M4와 같은 방식). 시뮬레이터는 같은 `.env`의 키를 쓴다 |
| B. 데모 경로는 키 확인을 건너뛰기 | `demo/*` 경로는 내부 주소에서만 허용하고 키를 묻지 않는다 |
| **C. 준비 스크립트가 실제 흐름을 밟기** | 스크립트가 공개 API로 가입 → 스트리머 신청 → 운영자 계정으로 승인 → 키 재발급을 실제로 하고, 재발급 응답의 키를 시뮬레이터 설정 파일(git 제외)에 적는다 |

| 기준 | A | B | C |
| --- | --- | --- | --- |
| 1. 데이터 구조 | 일반 회원·채널 행. 데모 표시 컬럼 | 데모 채널은 키가 없다(예외 데이터) | 일반 회원·채널 행. 데모 표시 컬럼 |
| 2. API 변경지점 | 없음(시작 코드 하나) | 키 확인에 예외 분기 | 없음 |
| 3. 상태관리 | 해당 없음 | 해당 없음 | 해당 없음 |
| 4. 핵심 동작: 확정 사양 | 신청·승인을 건너뛰어 "본인이 승인한" 계정이 아니다 | **같은 경로(키 확인)를 타지 않아 사양과 어긋난다** | 사양 그대로 |
| 4. 핵심 동작: 비밀 | 데모 키가 `.env`에 평문으로 있다 | 키 자체가 없다 | 데모 키가 시뮬레이터 설정 파일에만 있다 |
| 4. 핵심 동작: DB를 새로 만들면 | 앱이 다시 만든다 | 그대로 | 스크립트를 다시 돌린다 |
| 4. 핵심 동작: 만드는 순서 | 데모가 신청·승인 기능 없이도 뜬다 | 같다 | 가입·신청·승인·재발급 API가 다 있어야 한다 → 데모 이슈가 1주차 끝에 온다 |
| 5. 컴포넌트 | 해당 없음 | 해당 없음 | 해당 없음 |
| 6. 기존 패턴 | 계정 M4(운영자 계정 시작 때 생성)와 같다 | 없다 | 없다. 대신 서버 코드가 늘지 않는다 |
| 7. 테스트 용이성 | 시작 코드 통합 테스트 | 예외 분기 테스트 | 스크립트 자체가 1주차 기능 전체를 처음부터 끝까지 한 번 도는 확인이 된다 |

**추천: C.**
**C를 고르면 감수하는 것:** 데모 이슈는 가입·신청·승인·재발급 이슈가 다 끝난 뒤에야 할 수 있다. 스크립트를 다시 돌리면 키가 재발급되어 돌던 데모 송출이 끊긴다(시뮬레이터가 새 키로 다시 시작한다). 서버(배포)에서는 운영자 비밀번호로 스크립트를 한 번 돌려야 한다.
