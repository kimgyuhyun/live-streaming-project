## V1. 동시 시청자 수를 어떻게 세나

**풀려는 것:** 확정 사양 7절 — 지금 그 방송을 보고 있는 사람 수, 비로그인 포함, 최대 10초 늦게 반영, 탭 두 개면 2로 세도 된다. 서버 2대가 같은 값을 보여야 하고, 채널 페이지와 방송 목록이 같은 값을 읽는다. 확정 사양 미해결 항목 2.

**왜 비교가 필요한가:** 세는 위치(미디어 서버 / 채팅 연결 / 시청 화면)에 따라 정확도·부풀리기 내성·다른 기능 의존이 모두 달라진다. 한 번 정하면 방송 목록 정렬까지 이 값에 묶인다.

| 안 | 요약 |
| --- | --- |
| A. MediaMTX 시청 세션 수 | Spring이 몇 초마다 `GET /v3/hlssessions/list`를 불러 경로(`live/{채널ID}`)별 세션 수를 Redis에 적는다 |
| B. 채팅 WebSocket 연결 수 | 방송 화면이 채팅에 붙으면(비로그인은 읽기 전용) 서버가 연결 수를 Redis에서 방송별로 더하고 뺀다 |
| **C. 시청 화면의 신호(하트비트)** | 방송 화면이 5초마다 "보고 있다"(`POST`)를 보낸다. 탭마다 만든 시청자 ID를 Redis 정렬 집합(값마다 점수를 붙여 범위로 지우고 세는 Redis 자료형)에 마지막 신호 시각과 함께 넣고, 10초 안에 신호가 온 ID 수를 센다 |

| 기준 | A | B | C |
| --- | --- | --- | --- |
| 1. 데이터 구조 | Redis `viewers:{채널ID}` = 숫자. 주기 작업이 덮어쓴다 | Redis `viewers:{방송ID}` = 숫자(연결마다 +1/−1) + 서버별 연결 목록(서버가 죽으면 그 몫을 빼려고) | Redis `viewers:{방송ID}` = 정렬 집합(시청자 ID → 마지막 신호 시각). DB 변경 없음 |
| 2. API 변경지점 | 채널 조회·방송 목록 응답에 `viewerCount` | 같다 + 채팅 WebSocket | 같다 + `POST /api/channels/{id}/watching` |
| 3. 상태관리 | 해당 없음 | 채팅 연결을 시청 중 계속 유지 | 방송 화면이 탭별 시청자 ID(`sessionStorage`)를 들고 5초마다 신호 |
| 4. 핵심 동작: 나간 시청자가 빠지는 시간 | **약 30초**(잰 값 AD) + 조회 간격. 사양 10초를 넘는다 | 연결이 끊기면 바로. 서버가 죽으면 정리할 때까지 남는다 | 최대 10초(신호가 끊긴 ID를 센 때 지운다) |
| 4. 핵심 동작: 부풀리기 | 쿠키 없는 요청마다 세션이 생긴다(잰 값 AC). 스크립트 한 줄로 부풀린다 | 연결을 많이 열면 부풀린다. 연결 수 제한 필요 | ID를 바꿔 가며 신호를 보내면 부풀린다. **IP당 세는 ID 수를 제한**(예: 5개)해 막는다 |
| 4. 핵심 동작: 서버 2대 | 둘 다 같은 목록을 읽어 같은 값을 쓴다(멱등). MediaMTX 호출이 2배 | Redis 하나로 합친다. 죽은 서버 몫 정리가 필요하다 | Redis 하나로 합친다. 서버 상태에 기대지 않는다 |
| 4. 핵심 동작: 지금 만들 수 있나 | 된다 | **안 된다.** 채팅이 아직 없다 | 된다 |
| 5. 컴포넌트 | 해당 없음 | 채팅 칸이 늘 연결되어 있어야 함 | 방송 화면에 신호 훅(`useWatchingSignal`) 하나 |
| 6. 기존 패턴 | `MediaMtxClient`에 조회 하나 추가, `BroadcastReconciler` 같은 주기 작업 | 채팅 도메인에 묶인다 | `LoginAttemptLimiter`처럼 Redis로 세고 시간으로 지운다 |
| 7. 테스트 용이성 | MediaMTX 응답을 가짜로 바꿔야 한다. 세션이 닫히는 시간은 실제 MediaMTX로만 확인 | 채팅이 있어야 테스트할 수 있다 | Spring + Testcontainers Redis로 "10초 지난 ID는 안 센다"를 시계를 바꿔 바로 테스트 |
| 부하(시청자 1,000명) | 5초마다 목록 1번(세션 1,000개 JSON). 시청자가 늘수록 응답이 커진다 | 연결 1,000개 유지(채팅과 같이 쓰면 추가 비용 없음) | 초당 신호 약 200건(Redis 쓰기 2번씩). IP당 제한(초당 10건) 안이다 |

**추천: C.**
**C를 고르면 감수하는 것:**
- 시청자 1,000명이면 초당 약 200건의 요청이 Spring을 지난다. 실제로 영상을 보지 않고 화면만 열어 둔 탭도 센다.
- 영상만 직접 받는 클라이언트(VLC 등)는 세지 않는다.
- 채팅이 생기면 연결과 신호가 둘 다 돈다. 그때 B로 옮길지 다시 본다.
- **대비책·측정 계획:** k6로 시청자 1,000·5,000명 신호를 흉내 내 신호 API의 p95와 Redis CPU를 잰다. p95가 50ms를 넘으면 신호 간격을 늘리거나(10초 신호·20초 창 — 사양 10초를 넘으므로 사양과 같이 고친다) B로 옮긴다.

### 다시 비교 — 서버 부담 기준 (사용자 질문 "치지직·숲은 서버 부담이 없는 방법으로 세지 않나")

- 치지직·숲은 세는 방법을 공개하지 않았다. 트위치도 공개하지 않았고, 알려진 것은 "영상을 재생하고 있는 사람을 센다", "들어오고 나간 것이 반영되는 데 몇 분 걸릴 수 있다" 정도다.
- 시청자 수에 비례해 늘어나는 요청: A는 **없다**(시청자는 어차피 영상 조각을 받으러 MediaMTX에 계속 요청한다. 서버는 그 목록을 몇 초마다 한 번 읽는다). C는 시청자 1,000명에 초당 약 200건이다.
- A의 약점이던 "나간 시청자가 30초 남는다"는 사양을 "최대 1분"으로 바꿔 받아들인다(사용자 결정).
- A의 약점이던 부풀리기는 IP당 세는 세션 수를 제한해 막는다. MediaMTX 1.21.4에 `hlsTrustedProxies`(앞단 프록시가 넘긴 `X-Forwarded-For`를 진짜 주소로 믿는 설정)가 있다(바이너리에서 확인). 지금은 모든 세션이 nginx 내부 주소(`172.27.*`)로 보인다.
- 세션 목록은 페이지로 나뉜다(`itemCount`·`pageCount`·`itemsPerPage`). 끝까지 넘겨 읽어야 한다.

**선택: A.** 고른 안의 설계는 `prd/viewer.md` V1.

## V2. 방송 목록을 시청자 수 순으로 어떻게 줄 세우고 나눠 주나

**풀려는 것:** 확정 사양 9절 — 방송 중인 방송만, 시청자 수 많은 순, 같으면 먼저 시작한 순, 20개씩 더 불러온다. 시청자 수는 Redis(V1)에, 방송·채널은 DB에 있다. 시청자 수는 계속 바뀐다.

**왜 비교가 필요한가:** 정렬 기준이 DB 밖(Redis)에 있어서 SQL 한 번으로 정렬·나누기를 할 수 없다. 진행 중 방송이 몇 개냐에 따라 맞는 방법이 다르다.

| 안 | 요약 |
| --- | --- |
| **A. 진행 중 방송을 전부 읽어 Spring에서 정렬** | DB에서 진행 중 방송 전부(채널 이름·제목 포함), Redis에서 그 방송들의 시청자 수를 한 번에 읽어 Spring이 정렬하고 20개씩 자른다 |
| B. Redis 정렬 집합으로 순위 | Redis `live:viewers`(방송ID → 시청자 수)를 신호·종료 때 고쳐 두고, 순위 범위로 20개 ID를 꺼낸 뒤 DB에서 그 20개만 읽는다 |
| C. 시청자 수를 DB에 주기적으로 적기 | 몇 초마다 시청자 수를 `broadcast.viewer_count`에 쓰고, SQL `ORDER BY viewer_count DESC, started_at`으로 정렬·나누기 |

| 기준 | A | B | C |
| --- | --- | --- | --- |
| 1. 데이터 구조 | 변경 없음 | Redis 정렬 집합 하나 더(방송 종료 때 지워야 함) | `broadcast.viewer_count` 열 추가, 정렬 색인 |
| 2. API 변경지점 | `GET /api/broadcasts?page=` 하나 | 같다 | 같다 |
| 3. 상태관리 | 해당 없음(목록이 "더 보기"로 이어 붙인다) | 같다 | 같다 |
| 4. 핵심 동작: 요청 한 번의 비용 | 진행 중 방송 수 N에 비례(DB 1번 + Redis 1번) | 20개만큼(Redis 1번 + DB 1번) | 20개만큼(DB 1번) + 주기 쓰기 |
| 4. 핵심 동작: 값이 맞는가 | 목록과 채널 페이지가 같은 Redis 값을 읽는다 | 순위 집합과 V1 값이 어긋날 수 있다(두 곳에 쓴다) | 쓰기 간격만큼 채널 페이지 값과 다르다 |
| 4. 핵심 동작: "더 보기" 사이 순위가 바뀌면 | 같은 방송이 두 번 나오거나 빠질 수 있다(세 안 공통). 화면이 이미 받은 방송 ID는 다시 붙이지 않는다 | 같다 | 같다 |
| 5. 컴포넌트 | 메인 화면 방송 카드 목록 | 같다 | 같다 |
| 6. 기존 패턴 | `ChannelMapper.xml`의 진행 중 조회 그대로 | Redis 쓰기 경로가 V1 신호에 하나 더 붙는다 | `BroadcastReconciler` 같은 주기 작업 하나 더 |
| 7. 테스트 용이성 | 정렬 규칙이 Spring 안이라 단위 테스트가 쉽다 | 순위 집합 정리(종료·서버 재시작)까지 테스트해야 한다 | 주기 작업과 정렬을 따로 테스트 |

**처음 추천: A.** (진행 중 방송이 1,000개에서 p95 100ms를 넘으면 B로 옮긴다는 조건을 달았다)

### 추가한 안 D — V1(A)을 고른 뒤

사용자가 "문제가 생기면 옮기는 설계"를 받지 않았고, V1이 A(MediaMTX 세션을 주기적으로 모아 센다)로 정해졌다. 집계가 어차피 몇 초마다 모든 방송의 시청자 수를 한 번에 만든다. 그 자리에서 순위까지 만들면 B의 약점(값을 두 곳에 써서 어긋난다)이 사라진다.

| 안 | 요약 |
| --- | --- |
| **D. 집계가 만든 순위 스냅샷** | V1 집계가 5초마다 진행 중 방송 전체의 시청자 수로 Redis 순위 집합 하나와 방송별 수 해시 하나를 **새 판(버전)으로 통째로** 만든다. 목록은 그 판에서 20개씩 꺼내고, 채널 페이지는 같은 판의 해시를 읽는다 |

| 기준 | D |
| --- | --- |
| 1. 데이터 구조 | Redis `viewers:{판}:rank`(순위 집합), `viewers:{판}:count`(방송ID → 수), `viewers:current`(지금 판 번호). 판마다 2분 뒤 만료. DB 변경 없음 |
| 2. API 변경지점 | `GET /api/broadcasts?snapshot=&offset=`. 첫 요청은 지금 판, 응답에 판 번호를 담는다. "더 보기"는 같은 판으로 묻는다 |
| 3. 상태관리 | 목록 화면이 첫 응답의 판 번호를 들고 다음 묶음을 요청한다 |
| 4. 핵심 동작: 요청 한 번의 비용 | Redis 순위 범위 1번(방송 수 N에 대해 log N) + DB에서 그 20개만 1번. **진행 중 방송이 늘어도 한 묶음 비용이 거의 같다** |
| 4. 핵심 동작: 값이 맞는가 | 순위와 수가 한 판에서 같이 만들어진다. 목록과 채널 페이지가 같은 판을 읽는다 |
| 4. 핵심 동작: "더 보기" 사이 순위가 바뀌면 | **같은 판으로 묻기 때문에 겹치거나 빠지지 않는다.** 2분 넘게 머물러 판이 만료되면 지금 판으로 처음부터 |
| 4. 핵심 동작: 같은 시청자 수 | 사양 "먼저 시작한 순". 순위 집합의 값을 `{역순 시작 시각}:{방송ID}`로 넣어 점수가 같으면 먼저 시작한 방송이 앞에 온다 |
| 4. 핵심 동작: 서버 2대 | Redis 잠금(`SET NX` + 만료)으로 한 대만 집계한다. 그 서버가 죽으면 잠금이 만료되어 다른 서버가 이어 받는다 |
| 5. 컴포넌트 | 메인 화면 방송 카드 목록(판 번호를 들고 "더 보기") |
| 6. 기존 패턴 | 주기 작업(`BroadcastReconciler`), Redis 만료(`LoginAttemptLimiter`), 진행 중 방송 조회(`ChannelMapper.xml`) |
| 7. 테스트 용이성 | 집계(세션 목록 → 판)와 읽기(판 → 묶음)를 나눠 Testcontainers Redis로 테스트. "판이 바뀌어도 같은 판으로 물으면 겹치지 않는다"를 박는다 |

**선택: D.**
**D를 고르면 감수하는 것:**
- Redis 키가 판마다 생긴다(5초마다 하나, 2분 만료 → 최대 약 24판). 진행 중 방송 1,000개면 판 하나가 수십 KB라 합쳐도 수 MB 안쪽이다.
- 방송 제목·채널 이름은 판에 넣지 않고 그 20개를 DB에서 새로 읽는다. 판이 만들어진 뒤 끝난 방송은 DB에서 걸러 20개보다 적게 올 수 있다.
- 집계가 멈추면(잠금을 쥔 서버가 멈춤) 판이 만료될 때까지 숫자가 그대로다. 판 나이를 응답에 넣고, 2분이 지나면 목록은 DB 진행 중 방송을 시작 순으로 보여 준다(시청자 수 없이).
- **측정 계획:** 진행 중 방송 100·1,000개, 시청 세션 1,000·10,000개를 넣고 (1) 집계 한 번 걸린 시간, (2) 목록 API p95를 잰다. 집계가 5초를 넘으면 주기를 늘리고 사양 "최대 1분" 안인지 다시 본다.
